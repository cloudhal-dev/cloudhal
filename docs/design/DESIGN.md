# Cloudhal Studio design system

**Binding for every admin surface** (`apps/studio`, capability panels, docs UI). Cloudhal is a premium, community-facing product; its admin must read like the current Cloudflare dashboard. The implementation vocabulary is **Kumo** (`@cloudflare/kumo` 2.14; `pnpm kumo ls` and `pnpm kumo blocks` list its components and blocks) consumed through `@cloudhal/ui`. The official `kumo-design` skill (`.agents/skills/kumo-design`, installed from `cloudflare/kumo`) is part of this document; `apps/studio/test/design-rules.test.ts` enforces the mechanical rules in CI.

Verified sources: kumo-ui.com (installation, components-vs-blocks, blocks, component docs, registry), the Kumo repository (`sidebar.tsx`, blocks, the docs app shell), the kumo-design skill, Cloudflare dashboard documentation and changelogs (accounts/zones navigation, keyboard shortcuts 2026-05, navigation updates 2025–2026). Date: 2026-10-08.

## 1. Dashboard anatomy

The Cloudflare dashboard is: a **left sidebar** that is the primary navigation and whose contents switch between an *account surface* and a *zone surface* (a switcher sits at the top of the sidebar); **grouped, collapsible menus named by capability, not product**; a slim **top bar** with quick search (`/`, ⌘K) and the user menu; a **content area** with breadcrumbs, a page header (title, description, tabs, right-aligned actions), and **cards or tables**; resource lists carry a sticky right column with usage/help; empty states, skeleton loading, toasts and banners are system-wide.

Studio mirrors this one-to-one:

| Part | Kumo implementation |
|---|---|
| App shell | `Sidebar.Provider defaultOpen collapsible="icon" peekable mobileBreakpoint={768} className="h-dvh"` → `<Sidebar>` + a content column `flex h-full min-h-0 flex-1 flex-col overflow-y-auto overscroll-y-contain bg-kumo-overlay`. The provider must have a definite height because Kumo's `<aside>` is `h-full`; the column scrolls, the sidebar stays viewport-tall. **The document never scrolls**: the shell is `h-dvh` (the visible viewport, mobile toolbars included) and `#root` is `min-h-dvh` — with `h-svh`/`min-h-screen` the page was taller than a phone's visible area, so reaching the end of the column or the sidebar scrolled the whole document, half-hiding the top bar and opening an empty strip below. Scrolling never chains on: the column is `overscroll-y-contain`, the sidebar's viewport `overscroll-behavior: contain` (`@cloudhal/ui/styles.css`), `<body>` `overscroll-none`. The column is the page's scroll root (`usePageScrollRootRef` / `usePageScrollRoot` from `PageFrameProvider`); scrollspy and jumps use it, never `window`. The column is `relative`, so absolutely positioned bits in pages (`sr-only` labels in long tables) are contained by it — with the provider as their containing block they sat below a long list and made the document taller than the window (the "extra space after the end" on Snapshots). Sidebar 16.25 rem expanded, 57 px icon rail; `Sidebar.Header` is `h-12` like the top bar, so their bottom edges are one line. |
| Surfaces | *Account surface* (all sites) and *site surface* (one site); the switcher at the top of the sidebar is a `DropdownMenu` listing sites and "All sites". |
| Top bar | `header.sticky.top-0.z-10.h-12.shrink-0.border-b.border-kumo-line.bg-kumo-canvas`: `Sidebar.Trigger` (below `md`, the only way into the sheet), **the page's breadcrumbs** (`PageCrumbsSlot`; Kumo `Breadcrumbs` are `h-12`, exactly the bar), then right-aligned the `CommandPalette` button (⌘K and `/`; the palette, `CommandMenu`, loads with its first opening), the surface's actions (site surface: `SitePublish`, the Publish split button), the notification bell (`NotificationsBell`, §2n; its panel items, `NotificationItems`, load with the first bell that has something in it), the theme menu (`ThemeSwitch`: ghost icon button showing the current choice, `DropdownMenu` radio items Light / Dark / System; hidden below `sm`), the language `Select` (hidden below `sm`) and last the **user menu** (`UserMenu`: a circle ghost button with the person's `Avatar`, `DropdownMenu` with name + role, Account, Team, All sites, Theme and Language submenus, Sign out) — all `size="sm"`. The palette also offers "Theme: …" commands. On a site (RFC-0029 §7) it is Kumo's grouped palette (`Results` → `Group` + `GroupLabel` → `Item` / `ResultItem`):
  - **Groups.** Commands first (`useSitePalette`: the site's screens as a table, then New article, Create snapshot, Publish, All sites), then the site's content from `GET /api/sites/:siteId/search`, from two letters on, after 150 ms. Content comes one group per kind: Articles, Pages, Categories and tags, Media, Menu items, Redirects.
  - **A hit.** It shows its kind's icon, then where it lives (`breadcrumbs`: collection or taxonomy, path or slug, and Draft / In review). Enter or a click opens its editor; ⌘/Ctrl opens it in a new tab.
  - **Publish.** Publish opens `SitePublish`'s `ApprovalDialog`; the palette never publishes on its own.
  - **Footer.** It lists the keys.
  - **Matching.** Commands match with `foldName`, so case and Turkish İ/ı are folded. |
| Content container | `PageLayout` (`@cloudhal/ui`) — the only container: `mx-auto max-w-[1400px] px-4 py-6 sm:px-6 md:px-8 md:py-8 lg:px-10`, `width="narrow"` caps at 960 px. Screens never set `mx-auto`/`max-w-*` themselves (lint `page-container`). |
| Breadcrumbs | Built only by `Crumbs` / `SiteCrumbs` (`components/Crumbs.tsx`): "Cloudhal Studio › ui-audit › Pages › About", `Breadcrumbs.Current loading`, `Breadcrumbs.Clipboard` for the current resource id. Passed to `PageLayout crumbs`, which portals them into the top bar — never rendered in the content. |
| Page header | Kumo's `PageHeader` block (owned copy: every row flush with the content edge, 14 px description, `icon`, `actions`, controlled `tab`, loading title), rendered by `PageLayout` from its `title`, `description`, `icon` (24 px, top-level list pages only), `actions` (the page's primary action — "New page", "Create key" — lives here, never in the toolbar row) and `tabs`. Tabs are for **sub-views of one page only**; a tab bar that repeats the sidebar is forbidden (the old site tab bar was removed for that reason). |
| Lists | `PageLayout` (+ `aside` for usage/help: the `ResourceListPage` two-column body, 380 px sticky once the content is ≥ 64 rem) + `ListToolbar` (Kumo `Toolbar`, default size so it lines up with `Select`/`Button`) + `LayerCard className="p-0"` + `Table` + `Pagination`; empty → a bare `Empty` in the table's place. |
| Sections | `SectionCard` (`@cloudhal/ui`): Kumo `LayerCard` with the `Secondary` header row (title, optional 16 px icon, `actions` right: count `Badge`, ghost `LinkButton` "View all", small buttons) and the `Primary` body (`description`, `children` in `grid gap-5 px-5 pt-4 pb-5`, `flush` for a `Table`, `footer` row for Save/Discard). Never nested (lint `layer-card-nesting`); never a bare `LayerCard` with hand-made headers. |

Keyboard parity with the dashboard: `⌘K` / `/` open the palette; `t s` toggles the sidebar; `?` lists shortcuts (palette entry).

**Lazy message namespaces.** Every word goes through `useT()` (`apps/studio/src/i18n`), but not every word is in every page's first load. The core catalogs `en.ts`/`<locale>.ts` hold what the shell and most screens need, and only one language of them loads: English is in the first load (it is also every key's fallback), every other language is a dynamic import (`loadLocale`, found by file name) that `main.tsx` awaits before the first render and a language switch awaits before it applies; a feature whose wording only its own screens show keeps it in a **lazy namespace**: one top-level key, moved verbatim into `i18n/lazy/<ns>.en.ts` (`export const messages = { <ns>: { … } } as const`, the source of truth for its keys) and `i18n/lazy/<ns>.tr.ts` (`export const messages: NamespaceMessages<"<ns>"> = …`, so a missing or extra Turkish key is a type error), registered in `i18n/namespaces.ts` (one dynamic import per namespace and locale — a page fetches only the language it shows). Today: `analytics` (Analytics screen), `analyticsSettings` (site settings, Agents' "Allow analytics"), `readers` (editors' Readers card, overview card, list views column), `comments` (comment queue, thread, commenter, article editor card, Approvals) `commentsSettings` (site settings in every locale, Agents' "Allow comments") `appearance` (the color roles under site settings' Appearance form and its Header and footer section) `media` (the media library, a file's page, uploads, the image picker, takedowns; loaded with every route that shows them) and `menus` (the navigation editor and its dialogs, and menu references in the page, article and term editors, the page and article lists and the snapshot diff).
- **Reading.** A component that shows namespace words asks for them: `useT("analytics")` / `useI18n("readers")` returns a `t` typed for the core keys plus that namespace (`useT()` alone does not accept them, so a forgotten namespace is a type error) and suspends until the current locale's module is there. Text in another locale (the privacy notice) uses `useMessages([ns], LOCALE_LIST)` + `translate`.
- **Loading — no flash of keys.** The route that renders the namespace loads it with its chunk: `lazyRouteComponent(() => withMessages(import("./routes/X.tsx"), ["readers"]), "X")` in `router.tsx` (in parallel, also on hover preload), so the screen never suspends for words; if one is missed, the component suspends to the route's pending state rather than showing keys. A language switch first loads, in the new language, every namespace loaded in the old one, then switches (in a transition). `bundle-budget.ts` fails the build if `i18n/lazy/` reaches the initial load.
- **No hard-coded words** (AGENTS.md hard rule 10). Nothing a person reads is a literal in `apps/studio/src` or `packages/ui/src`: JSX text and string children, `aria-label`, `title`, `placeholder`, `alt`, `label`, `description`, `content` and every `…Label`/`…Text`/`…Title`/`…Description`/`…Placeholder`/`…Message`/`…Hint` attribute or property, tables of labels (`{ draft: "Draft", … }`), default values and `??`/`||` fallbacks, toasts and `confirm()`, `document.title`. Blocks take every word as a prop and have no English fallback (`StatusBadge label`, `DeleteResource labels`, `ApprovalDialog confirmLabel`/`cancelLabel`). A failed request is worded by `apiErrorText(t, error)` (`lib/api-errors.ts`: `errors.api.<code>`, then the server's message, then the status), never `error.message` directly. Search folds text with the Studio locale (`usePaging`'s `fold`, `toLocaleLowerCase(locale)`), never `toLowerCase()`. The `i18n` rule of the design lint (`apps/studio/scripts/i18n-lint.ts`) parses every `.ts`/`.tsx` of both trees with oxc and fails `pnpm check`; ids, keys, class lists, URLs, protocol values and logs are not prose and pass. A literal that reads the same in every language goes in its `ALLOWED` list (product and format names) with a reason, or carries an `i18n-ignore: <reason>` comment on its line or the line above.
- **Message syntax** (RFC-0032, ADR-0032). A catalog value is text with `{name}` arguments, or an ICU MessageFormat 1 message: `{count, plural, =0 {…} one {# file} other {# files}}` (the CLDR categories of the language; `#` or `{count}` is the number in the locale), `{kind, select, page {…} other {…}}`, `{n, selectordinal, …}`, `{n, number}` / `{n, number, percent|integer|compact}`. `other` is required; a literal brace is quoted, `'{}'`. `@cloudhal/messages` compiles the catalogs at build time (the `catalogs()` Vite plugin in `vite.config.ts` and `vitest.config.ts`), so no parser ships. `t()` is typed per key from `src/i18n/generated/params.ts` (`pnpm gen`; a plural argument is a `number`, a select one of its values); a message a block fills in itself keeps its placeholders with `keep("name")`. A count is one `plural` message called with the number (`t("editor.words", { count })`), never a `…One` key or a `count === 1 ?` ternary (the test rejects `…One`/`…Many` keys). When a translation needs another grammatical form of a data argument (Turkish names a role once, `{role}`, where English says `{roles}`; a taxonomy's own singular and plural labels), English declares it in `forms` (`en.ts`, by key prefix): the form becomes a required parameter of those keys and the only substitute a translation may use. A word that changes with a value is a `select` over the value with whole sentences (`{action, select, approve {… approved} … other {…}}`), never a translated word injected into a sentence. A translation that cannot use an argument at all (a Turkish case suffix on an arbitrary name) declares it in its core catalog's `dropped`, with the reason; the test rejects any other missing argument and any stale entry. A list a person reads goes through `listOf(items)` (`Intl.ListFormat` in the Studio language: "a, b, and c", "a, b ve c"; `formatList(locale, …)` from `@cloudhal/messages/format` outside React), never `items.join(", ")`; `" · "` between separate facts is a visual separator and stays. Numbers, dates, times, relative times, display names and collation come from the cached, locale-taking layer in `@cloudhal/messages/format` (`formatNumber`, `formatDate`, `formatRelative`, `numberFormat`, `dateTimeFormat`, `relativeTimeFormat`, `displayNames`, `collator`; `NUMERIC_DATE`/`NUMERIC_DATE_TIME` for what `toLocaleDateString`/`toLocaleString` showed), always with the Studio locale (or a fixed one for machine formats such as the `en-CA` day keys), never `new Intl.*` or `toLocaleString()` in a screen or block. The design lint enforces these: `i18n-format` (a formatter built on the spot), `i18n-plural` (two messages chosen by whether a number is 1) and `i18n-concat` (a sentence assembled from several `t()` results, or a list joined with `", "`), in `pnpm check`, `pnpm design:lint` and the agent hook; a reviewed exception carries `i18n-ignore: <reason>`. `test/i18n-messages.test.ts` checks every language: valid syntax, English's argument kinds kept, every plural category of the language present.
- **Adding keys.** Keys go in English and in every registered language (core: `en.ts` and each `<locale>.ts`; a lazy namespace: each `lazy/<ns>.<locale>.ts`, never back into the core catalogs; `test/i18n.test.tsx` checks keys and placeholders for every language). A branch made before a namespace moved (e.g. `analytics.bots.*` added under `analytics` in `en.ts`/`tr.ts`) merges by moving its lines unchanged into `lazy/analytics.en.ts`/`lazy/analytics.tr.ts` — the blocks keep their indentation there. A new feature with more than a few kilobytes of wording, shown on its own screens, starts as a lazy namespace; words the shell shows (navigation, commands) stay core (`nav.analytics`, `commands.goAnalytics`).
- **Languages.** `i18n/locales.ts` is the registry: one entry per language, keyed by its BCP 47 tag (also `<html lang>`, every `Intl` formatter and `calendarLocaleProps`, so dates and numbers follow the Studio language, never the browser's), with its native `name`, `dir` (set on `<html dir>`), `fallback` chain (always ending in English) `reviewed` and, where formatting needs it, an `intl` tag (Arabic and Persian `…-u-nu-latn`, Western digits, ADR-0033; `setIntlTags` makes every formatter of `@cloudhal/messages` use it). Besides English (the source) and Turkish (the owner's), every language is an AI translation awaiting review by a person who speaks it (`reviewed: false`, ADR-0034; the first right-to-left one is Arabic). The language menus show each name in itself only; that a language is an unreviewed AI translation is a comment on its registry entry, for maintainers. Loaders are not written by hand: `import.meta.glob` finds `i18n/<locale>.ts` (`export const messages: Messages`) and `i18n/lazy/<ns>.<locale>.ts`; `bundle-budget.ts` keeps every core catalog but English out of the first load. Studio opens in English, its global default, for everyone: the browser's language is not consulted; a person's own choice in the language menu is stored and wins (`matchLocale` remains for matching a tag to a registered language).
- **Pseudo-locale and catalog checks** (the i18n review's Phase 5). On a dev server (and in tests) `?pseudo` or `localStorage["cloudhal.studio.pseudo"] = "1"` shows every catalog message as "[Šààṽéé]" — accented, about a third longer, bracketed — generated from the compiled English messages (`@cloudhal/messages/pseudo`) with every argument and plural kept: plain English on screen is a hard-coded word, a missing "]" is a cut-off label, a broken layout has no room for German. It is never a language in the menus, and production builds do not contain it (`import.meta.env.DEV`; the bundle budget fails if the module reaches a chunk). `SHOTS_PSEUDO=1 pnpm design:shots -- …` takes the screenshots in it. `test/i18n-messages.test.ts` also fails on an **unused key**: `apps/studio/scripts/i18n-usage.ts` collects every literal and template key in Studio's code (string constants resolved, a literal naming a group reaches the group); `node apps/studio/scripts/i18n-usage.ts` lists them. Missing keys and placeholder parity were already checked (types, `test/i18n.test.tsx`).
- **Right-to-left readiness** (ADR-0033 D and B). Studio and the `@cloudhal/ui` blocks use logical utilities only — `ms`/`me`, `ps`/`pe`, `start`/`end`, `text-start`/`text-end`, `border-s`/`border-e`, `rounded-s`/`rounded-e`/`rounded-ss`… — never `ml`/`mr`, `pl`/`pr`, `left`/`right`, `text-left`/`text-right`, `border-l`/`border-r`, `rounded-l`/`rounded-r` (lint `rtl-logical`; `scripts/i18n-codemod/logical-utilities.ts` converts; an element placed by Floating UI in physical coordinates keeps `left-0` with an `i18n-ignore` reason). `<html dir>` and Base UI's `DirectionProvider` (in `KumoLocale`, through `@cloudhal/ui`) follow the locale registry's `dir`. `SHOTS_PSEUDO=rtl pnpm design:shots -- …` (or `?pseudo=rtl` on a dev server) renders the right-to-left pseudo-locale to find what does not mirror. Kumo's own components are made logical by the generated patch (`node scripts/kumo-patch.ts`, ADR-0033 A1; `kumo-upstream-notes.md` §7); Icons that mean a direction in reading order — back and forward, previous and next, "from → to", a closed tree row, opening a row, reply, indent, opening elsewhere, signing in and out, sending — go through `DirectionalIcon` (`<DirectionalIcon icon={ArrowRight} />`, or `directional(ArrowRight)` where a prop or table takes an icon component), which sets Phosphor's `mirrored` from Base UI's direction (ADR-0033 C1, lint `rtl-icon`). Physical and temporal directions stay as they are: up and down, sort order, clocks, refresh and undo circles, a chart's trend; such an icon among the matched names carries an `i18n-ignore` reason. Kumo's own ten directional icons (submenu, sidebar, pagination, date range, command palette) and the breadcrumb separator mirror through `rtl:-scale-x-100` from the hand-written `patches/kumo/rtl-icons.patch`, which reads `<html dir>` rather than Base UI's context (`kumo-upstream-notes.md` §7). Arrow keys follow the direction too: blocks whose Left and Right mean previous and next, open and close, or nest and move out (`MenuTree`, `CalendarMonth`) read the key through `readingKey(key, useDirection())`, and their help text names the keys as they work in the language (`menus.tree.instructionsRtl`).
- **Translation workflow** (ADR-0034). **Only English is edited by hand** (`en.ts`, `lazy/<ns>.en.ts`). Every other catalog is generated by `pnpm i18n:import` from translation files — nested ICU JSON, `.i18n/<locale>/<core|namespace>.json`, written by `pnpm i18n:export` with `.i18n/descriptions.json` (English text and the note above each key) — and carries a hash of its messages: a hand edit fails `pnpm check` (`node scripts/i18n-exchange.ts check`, run by `test/i18n-messages.test.ts`). The import checks keys and ICU syntax before writing anything, keeps a catalog's own exports after its messages (Turkish `dropped`), formats the files and runs the catalog tests. New English keys: export, translate the new keys in each language's JSON (by hand or with the `translate` skill, `.agents/skills/translate`), import. The translation platform (Weblate or Tolgee) and its hosting wait for the owner; the exchange format is the one it will read.
- **Adding a language** (the i18n review's Phase 6): (1) **prerequisites** — a language with plural categories beyond one/other (ar, ru, uk, pl, cs, …: `Intl.PluralRules(…).resolvedOptions().pluralCategories`) waits for ICU plurals (the review's Phase 1), a right-to-left one (ar, he, fa, ur) for logical CSS and Kumo's direction support (Phase 3); (2) add the registry entry with `reviewed: false`; (3) `pnpm i18n:export`, write `.i18n/<locale>/*.json` (the `translate` skill drafts them; an AI translation is fine as a first draft; its registry entry says so in a comment until reviewed), `pnpm i18n:import --locale <locale>` — it generates `i18n/<locale>.ts` and every `lazy/<ns>.<locale>.ts`; (4) `pnpm --filter @cloudhal/studio typecheck` and `test/i18n.test.tsx` (keys, placeholders, no English sentences left, every namespace present); (5) `vite build` — the bundle budget must not move (the language loads only for its users); (6) `pnpm design:shots` in the language at 1440 and 390 px (German and Finnish run long); (7) a speaker reviews in context, then `reviewed: true`.

### 2a. Resource list (sites, pages, articles, snapshots, activity, agent keys, skills)
```tsx
<PageLayout crumbs={…} icon={<Icon size={24} />} title description
  actions={<Button variant="primary" icon={<Plus />}>New page</Button>}
  aside={<SectionCard title="From the terminal" icon={<TerminalWindow size={16} />}>…<Code /></SectionCard>}>
  <ListToolbar search onSearch placeholder actions={…Select filters, RefreshButton…} />
  <LayerCard className="p-0"><Table><Table.Header><Table.Row><Table.Head/>…<Table.Head sticky="right"/></Table.Row></Table.Header>
    <Table.Body>{rows.map(r => <Table.Row key={r.id}><Table.Cell><Link href>{r.title}</Link></Table.Cell>…<Table.Cell sticky="right"><RowMenu /></Table.Cell></Table.Row>)}</Table.Body></Table></LayerCard>
  <Pagination page perPage={25} totalCount setPage controls="full" />
</PageLayout>
```
Empty → a bare `Empty icon={<Icon size={48} />} title description commandLine contents` in place of the table (Kumo `Empty` draws its own frame — never wrap it in `LayerCard`); inside a card, cell or dialog use `SectionEmpty` (frameless). Never pass `className` to `Empty`. Loading → `TableSkeleton` (a `Table.Body`, so always inside `<Table>`). Times in lists are relative (`RelativeTime`) with the absolute time in a `Tooltip`. Every control on one toolbar row has the same height (Kumo default size).

Multilingual sites (`site.locales.length > 1`, an internal review (2026-10) §4a): Pages and Articles show one row per translation group (`lib/translation-groups.ts`), by its default-language version or the original, with a "Languages" column of `LanguageChips`. The toolbar gets a language `Select` ("All languages (grouped)" by default, or one language: that language's versions as a flat list, without the Languages column); picking a language makes it the site's **working language** (`lib/working-language.ts`, this browser only), which new pages and articles start in. Single-language sites show neither.

Snapshots: the primary "Create snapshot" opens a `LayerDialog` (optional label `Input` + `Radio appearance="card"`: keep the live site / publish it); publishing continues into `ApprovalDialog` before anything is sent. `SnapshotTimeline` rows keep Compare (ghost) and Publish/Roll back (secondary) in separate trailing columns so actions align, the last one `sticky="right"`; times via its `renderTime` prop (`RelativeTime`).

### 2b. Resource detail / editor
`PageLayout` (crumbs via `SiteCrumbs` with `copy={id}`; title; description = status badge (+ "Ended (collection rule)", §2ah) + path in mono; actions = `PreviewToggle`, `StatusActions` — a secondary "More actions" ⋯ `DropdownMenu` with a "Status" group plus Duplicate and Delete, and the next lifecycle step as a labelled secondary button, Publish via `ApprovalDialog` — and the primary Save with `loading`, disabled until dirty) → `EditorLayout`. ### 2c. Settings / form
Same header; `Columns variant="1-2"` (a fixed 13 rem sticky `TableOfContents` and cards capped at 56 rem, side by side once the page container is ≥ `@4xl`); one `SectionCard` per section, `Switch` for instant settings, `SensitiveInput` for secrets, `ClipboardText` for ids; sticky footer `border-t border-kumo-line` with `Button variant="primary" type="submit" loading`.

Text inputs in cards get `className="w-full"` so they never overflow the card at 375 px; field pairs use a container-query grid (`@container` → `@lg:grid-cols-2 items-start`), each field with its own description so rows stay aligned.

### 2g. Credentials (agent keys) — modes, create, one-time reveal
Every key has a **mode** (ADR-0015) — how independently the agent works; scopes stay the hard limit and a mode never grants more. Studio offers the four key modes, in order of autonomy: `plan` (read + preview), `manual` (every change waits), `edits` (default: edits free, publish/rollback/delete wait), `auto` (like edits, small article-only publishes go live without a person). `bypass` is never offered or sent for a key (the API answers 400); it is only *explained*, with `cloudhal mcp --mode bypass`.

- **Approve** on `publish`, `rollback`, `delete_page`, `delete_entry` opens `ApproveRequestDialog` (`LayerDialog`): the prompt in an `InsetPanel`; for publish the approximate changes (live snapshot → newest snapshot: count badges + "View changes", labelled as an approximation because edits after the newest snapshot are not counted); for rollback the target snapshot with "View changes"; for deletes the target id; and an info `Banner` "Single use, for the site as it is now" (void if anything changes before the agent calls again). `request_elevation` has its own dialog (below). Other tools and Deny act immediately with a toast.
- **409** (decided, used or expired meanwhile): error toast "This request is no longer pending", the dialog closes, the list refetches.
- **Elevation requests** (`tool: "request_elevation"`, ADR-0016 addendum; `ElevationRequest.tsx`) are a different kind of request and look it. The server's English prompt is never shown. The left cell is laid out like `ToolCell`: a 16 px `ClockCountdown` icon with "Elevation request" and the raw `request_elevation` in mono below; History uses the same cell. The body shows, in order:
  - the change as two full `ModeBadge`s, "Edits → Auto". The own mode comes from `/api/agent-keys` (`input.keyId`), else the prompt's "its own mode is …", else the request's `mode` (`requestOwnMode`);
  - a localised sentence, "Desk asks to work in Auto mode for 1 hour.";
  - the agent's reason as `AgentReason` (recessed `InsetPanel`) labelled "The agent's reason", quoted, as **plain text** (agent-controlled);
  - a muted line on what approving does. When the key's own mode has caught up with the request meanwhile, `Banner variant="secondary" size="sm"` instead says there is nothing to grant and to deny it;
  - in the meta row, `ClockCountdown` "If you approve now: until 14:30".

  **Approve** always opens `ApproveElevationDialog` (`LayerDialog size="base"`); **Deny** stays one click. Top to bottom, the dialog has:
  - `AgentReason`;
  - **Mode** with the requested `ModeBadge`, fixed (no picker), and "To grant another mode, deny this request and elevate the key from Agents.";
  - `AutoModeConfirm` when the mode is `auto`;
  - **Duration**: "Requested: 1 hour. Shorter is fine, longer isn't possible.", then segmented `Tabs` with the standard presets shorter than the request plus the request itself, preselected (`grantPresets`; an odd request reads "1 hr 30 min" in the presets' words), then Custom. Custom has the elevate dialog's number + unit fields, bounded by the server minimum and the request ("At most 1 hour");
  - an outline `InsetPanel` summary "Now [own] → Elevated [mode]", the bold "Desk works in Auto mode until 14:30, then back to Edits." and "Applies on the agent's next call…".

  The primary action is "Grant elevation" (`loading`). The POST sends `{minutes}` only when shortened. Errors:
  - A **400** stays in the dialog as `Banner variant="error"`.
  - A **409** shows the server's message plus "The request stays in the list while it is pending…", and refetches approvals and keys. If the refetch shows the request is no longer pending, the dialog closes with the "no longer pending" toast.

  On success, a toast "Elevation granted · Desk works in Auto mode until 14:30, then back to Edits." and approvals, agent keys and activity are invalidated. CI checks that the dialog is the only caller of `api.approvals.grantElevation`, renders `AutoModeConfirm` with its guard, never sends more than requested, and that the page routes elevation approvals to it first.
- **History**: flush `SectionCard` (ClockCounterClockwise icon) with a `Table` (or `SectionEmpty`): request (tool + truncated prompt in a `Tooltip`), status dot `Badge` (approved success, denied error, used neutral, expired warning), agent, requested, decided (time + "by you" or the deciding actor id). Elevation requests read `ClockCountdown` "Elevation request" over "Elevation to Auto · 1 hour" (the requested time), and a used one is "Granted" (success).
- **Overview**: while requests wait, `Banner variant="alert"` with a hand icon and `Banner.Action` "Review requests" above the cards.

### 2n. Notifications (top bar bell; ADR-0016 addendum "told before it ends")
`GET /api/notifications` lists what needs the signed-in person: their elevations ending within `noticeMinutes` (`elevation-ending`) and agents asking to elevate one of their keys (`elevation-request`). Items carry stable ids. Studio reads it with one query (`useNotifications`, key `["notifications"]`), owned by the bell, so it runs only while someone is signed in: every 60 s, every 15 s while an elevation is ending, also in a background tab (`refetchIntervalInBackground`) so browser notifications can arrive. A 404 (older server) is "no notifications": nothing is fetched again — not on an interval, on focus or on remount.
- **Bell** (`NotificationBell` block, `@cloudhal/ui`): a ghost square `Button size="sm"` with a 16 px `Bell` in the top bar, between the surface's actions and the language select, on every surface and at every width. A count `Badge variant="primary"` sits on its corner (hidden at 0, "9+" above 9); the button's name carries the count ("Notifications (2)").
- **Panel**: Kumo `Popover` (`align="end"`, `positionMethod="fixed"`, 24 rem, at most the viewport minus 1 rem) without its own padding: a header row (`Popover.Title` "Notifications", a secondary count `Badge`), a scrolling list of `NotificationItem`s divided by `divide-kumo-hairline` (max 32 rem / 70 svh), and a footer row with a ghost "Notification settings" that opens Account › Notifications. Empty: `SectionEmpty` with `BellSimple` "You're all caught up". Items whose end or expiry has passed drop out before the next poll.
- **`NotificationItem`**: a 16 px tone icon aligned with the first line (`warning` `ClockCountdown` for an ending elevation, `info` `Robot` for a request), a bold title with optional meta on the right, the body, then one row of `size="sm"` actions that wraps on phones.
  - *Elevation ending soon*: `ModeBadge` of the elevated mode + warning `Badge` `ClockCountdown` "8 min left" (recomputed from `until`), then "Desk's Auto mode ends in 8 min (14:30), then back to Edits." Actions: a `ButtonGroup` — secondary "Extend 1 hour" and a ▾ `DropdownMenu` with a "Counts from now" group of 30 min / 1 hour / 4 hours, each with its new end ("4 hours · until 18:30"); secondary "End now"; ghost `LinkButton` "Open Agents". Extend and End disable each other while pending.
  - *Agent asks*: "Planner asks for Edits · 30 min" with `RelativeTime` as meta, the reason in `AgentReason` (recessed `InsetPanel`, **plain text**: agent-controlled), and a secondary `LinkButton` "Review" to that site's Approvals.
- **Extend = re-post the mode in force** (`useExtendElevation`, `components/elevation-actions.ts`, re-exported by `components/Elevation.tsx`): `POST /api/agent-keys/:id/elevation {mode, minutes}` with the elevated mode and the preset clamped to the server's bounds; it replaces the elevation in force and counts from now. The keys are read first, and an elevation that has ended or changed mode is refused with an error toast ("This elevation has already ended") — re-elevating is a new grant, and new grants (with the Auto consent) only happen in the elevate dialog. **End** is `useEndElevation`. Both toast, update the key list and invalidate `agent-keys`, `notifications` and `approvals`; deciding an approval invalidates `notifications` too. The bell, its toasts and the Agents banner never call the API for elevations themselves (CI checks).
- **One-time toasts** (`useNotificationAlerts`, hosted by the bell): an id seen for the first time while Studio is open raises a notice toast once — `warning` "Desk's Auto mode ends in 8 min" / "At 14:30 it goes back to Edits…" with the actions "Extend 1 hour" and "Open Agents"; `info` "Planner asks for Edits · 30 min" with the quoted reason and "Review". The toast carries the item's id (Kumo shows an id once), stays 15 s, and an action closes it. Whatever is there on the session's **first** answer is not announced (the bell lists it). Announced ids are remembered per browser in `localStorage` (`cloudhal.studio.notifications.shown`, last 200, every access in `try/catch`), so a reload never repeats one. New items also refresh the key list or approvals.
- **Browser notifications** (opt-in, Account › Notifications): turning the switch on calls `Notification.requestPermission()` from the click; the choice lives in `localStorage` (`cloudhal.studio.notifications.browser`). For each newly announced id, when the person opted in, permission is `granted` and `document.visibilityState !== "visible"`, Studio raises `new Notification(title, {body, tag: id})` with the toast's words; clicking it focuses the window and opens Agents or the site's Approvals. A visible tab gets only the toast. Delivery beyond an open tab (email, push) is not Studio's job yet.

### 2s. Role gating (RFC-0005 I16)
The server decides; Studio only hides or disables what it would refuse **and says why**.
- **Source**: `GET /api/me` (`useMe`, query `["me"]`) — `role`, `scopes`, the `can` ability map, `invitableRoles`. `useCan(ability)` reads it; anything not known to be denied (loading, older servers) reads as allowed. `useGate(ability)` adds the reason, built from the least senior role that has the ability (`minimumRole` over `/api/instance` → `roles`): "Only Editors and above can publish others' work." Screens never compare role names (CI checks); only the Team screens do.
- **Patterns**: a gated `Button` is `disabled` with `title={gate.reason}` (Kumo wraps a disabled titled button in a `Tooltip`; CI checks every `disabled={!x.allowed}` carries its reason); a gated menu item stays in place, disabled, its `Tooltip` on a `render={<div />}` wrapper; a screen the person may read but not change gets `ViewOnlyBanner` (secondary, `LockSimple`, "You can view this" + the reason) and its controls go inside `ReadOnly` (a disabled `<fieldset>`: inputs, buttons and menu triggers off at once, links still work). Sidebar items stay enabled: every member may read every screen.
- **Where**: pages and the page editor (`pages.write`), categories/tags, the term editor and redirects (`structure.write`), site settings General and Domains (`settings.write`; preview links stay), the tags migration (`settings.write`), others' articles (`entryAccess`: Editors any, Authors their own, Contributors their own until published — the editor shows `ViewOnlyBanner` and a disabled fieldset, and the articles list disables Delete).
- **Publishing** (`usePublishMode`, `usePublishSite` in `components/Publish.tsx`): Editors and above "Publish"; an Author "Publish" when Studio's guess (`ownOnlyGuess`: only their own published articles changed since the live snapshot) says own-only, else **"Request publish"** with its own confirm copy ("Your changes include work by others…", "Send request"); a 202 shows an info notice "Publish requested — an Editor must approve" with "Open Approvals". A Contributor sees Publish disabled with the reason; in the article editor the draft step reads **"Submit for review"** and Publish stays disabled ("An Editor publishes yours after review"). Snapshot rows use `SnapshotTimeline`'s `publishDisabledReason` / `rollbackDisabledReason`.
- **Approvals**: `canDecide === false` disables Approve (and Deny, unless it is the person's own or their agent's request) with a reason line under the meta (`approvals.decide.*`: own request, not the key's creator, mode above the role, missing scope, not own); a 403 `cannot_decide` toasts the same words. A person's own request (cause `role`) shows a warning `Badge` `Hourglass` "Waiting for an Editor", "{name} wants to publish the site." and why their role can't alone (from the server's reason), and **Withdraw** instead of Deny/Approve. Approving such a request publishes it ("Approved and published"); 409 `state_changed` says the site moved on. People's names carry their `RoleBadge` (from `GET /api/members`) here and in Activity.
- **Agent keys**: `useAgentModeRules` carries the person's cap — `keyModes` stops at it (a Contributor's picker shows Plan, Manual, Edits and `RoleCapHint` "Your role allows agent keys up to Edits mode"), elevations offer only modes up to it, and the Elevate item is disabled with that reason. The scope picker shows each scope as the role grants it (`scopeOptions`): an own variant in place of the full scope ("Your role gives content:write only for your own work"), or the scope disabled ("Your role can't give this to a key"). A key whose `effectiveScopes` are narrower than its stored scopes shows the effective ones with a warning `Badge` "Narrowed by role" (tooltip: the creator's role now, and what it was given). Administrators get **Your keys | All keys** tabs; All keys lists every key with a "Created by" column (`Avatar`, name, `RoleBadge`) and a menu with End elevation and Revoke, while Elevate stays disabled ("Only the person who created this key can elevate it").
- **Activity**: without `audit:read` a secondary `Banner` "Your activity — Editors and above see everyone's".
- **Notifications** (§2n): `member-joined` (success `UserPlus`, "Ada joined", the role badge, "Open Team") and `role-changed` (info `ShieldStar`, "Your role is now Author", Editor → Author badges, who changed it); a new `role-changed` refetches `/api/me`, the members and the keys, so gating follows at once.
- **Account**: the profile shows the person's role as a `RoleBadge` row; the account menu's header shows the name and the role.

### 2w. Comments (RFC-0007 §14, ADR-0022)
Reader comments live outside the graph (D1/SQLite), are read and moderated by people over REST and by agents over MCP, and every comment, name, report and agent note is **untrusted reader text**. The **blocks** (`@cloudhal/ui`, below) and the **screens** (end of this section) are built. Words go through two lazy namespaces (§1): `comments` (queue, thread, commenter, approvals, editor card) and `commentsSettings` (settings); the shell keeps `nav.comments` and `commands.goComments`. Blocks take every word as a prop — one shared `CommentWords` object (status names, label names and hints, who set a label, author kinds, "In reply to …", "This comment was removed", the untrusted-text panel …) that the screens build once from `useT("comments")`, plus a small `labels` object per block — and a `locale` for `Intl` (relative and absolute times, counts, percentages). They live in the main entry and, like the analytics blocks, are listed in `bundle-budget.ts`'s `LAZY_ONLY` (`Comment*`, `ArticleCommentsSummary`, `comment-model`), so only the lazy comment routes and the editor card load them; `BulkActionBar` is generic and not listed.
- **Plain text, always.** `CommentText` is the only way comment text reaches the screen: paragraphs on blank lines, line breaks kept, `dir="auto"`, and the public page's link rule (`comment-model.ts`): only `https:` URLs with a host and without credentials become native anchors (`target="_blank" rel="ugc nofollow noopener noreferrer"`, a screen-reader "opens in a new tab"); `http:`, bare `www.`, `javascript:` and markup stay literal text. Rendered as React text nodes — no `dangerouslySetInnerHTML` (lint `no-html-injection`; `packages/ui/test/comments.test.tsx` also scans the comment blocks). `clamp={2}` folds breaks into spaces for the queue's two-line excerpt (full text in a `Tooltip` or the thread). Report details and moderator notes are plain text too (`whitespace-pre-line`, never linkified). Until `@cloudhal/comments` exports its `linkify`, the rule lives in `comment-model.ts`; the renderer and Studio must share one function (RFC-0007 §14), so the block switches to the package's when it lands.

It is not an instruction." (RFC-0007 §11.2). The approval dialog for comment tools uses the same panel around the full text.

Labels never change what readers see, so they never take a status colour's place.

Slots: `renderActions`, `renderDetails` (history, reports, statement of reasons), `renderReply` (the staff reply form under the comment answered), `selection`. States: `loading` (skeleton rows and a `role="status"` line), `empty` (`SectionEmpty`), `error` (an error `Banner` with "Try again").

### 2x. Schedules (RFC-0008 §15, ADR-0023)
Releases, embargoes, scheduled publishing and automations on one calendar. The **blocks** are in `@cloudhal/ui` (below); the **screens** (RFC-0008 §15.1) are described at the end of this section. Blocks take every word as a prop — one shared `ScheduleWords` object (kind names and the state names of releases, automations, runs and approvals) that the screens build once from `useT("schedules")` (a lazy namespace, §1), plus a small `labels` object per block — and dates as plain values: instants as RFC 3339 strings placed and timed in the site's `timeZone` (IANA, `Site.timeZone`, UTC when absent), calendar days as `YYYY-MM-DD`, a `locale` for `Intl` and `weekStartsOn` from `firstDayOfWeek(locale)` (Monday in Turkish). There is no date library: day arithmetic runs on UTC-midnight calendar dates (`schedule-model.ts`), names and times come from `Intl` (24-hour where the locale is, `hourCycleOf`), recurrence is expanded by the server and only shown (`NextRuns`). The blocks are in `bundle-budget.ts`'s `LAZY_ONLY`, so they load with the lazy schedule routes and the lazily loaded "Schedule…" dialog, never with the shell (about 44 kB minified, 14 kB gzip for all twelve, Kumo and icons aside); the calendar inside `DateTimeField` is Kumo's `DatePicker`, `React.lazy` like the analytics range's.
- **Visual language** (RFC-0008 §15.3): **fill = certainty, tone = state, icon = kind and origin; colour is never the only signal** (WCAG 1.4.1). `scheduleLook` maps an entry to one of nine looks: `quiet` (scheduled by a person or approved: `bg-kumo-tint`, the kind icon — publish and embargo `CalendarCheck`, expiry `CalendarX`, release `Package`, automation `Robot`), `auto` (the same + `Lightning`, the `AutoApprovedBadge` language), **`proposed`** (draft or waiting for approval: a **dashed `border-kumo-warning` outline with no fill**, `Robot` for an agent's + `HandPalm`), `struck` (denied, expired, canceled, skipped, stopped: `line-through`, `text-kumo-inactive`; hidden by default views, `isHiddenByDefault`), `danger` (conflict `Warning`, failed `WarningCircle`, missed `ClockCounterClockwise`, broken `LinkBreak`: `bg-kumo-danger-tint`), `running` (`bg-kumo-info-tint` + a turning `CircleNotch`, still under `prefers-reduced-motion`), `done` (published, ran: `bg-kumo-recessed`, muted), `ghost` (a future recurring occurrence: outline ring only, `ArrowsClockwise`) and `paused` (the ghost with `Pause`). **The dashed outline (D14)** is drawn only inside `ScheduleItem`, as `border border-dashed` without any shadow, because §4's `ring` edges cannot be dashed. The design lint's `shadow-borders` and `no-ad-hoc-surface` rules apply to screens, not to `packages/ui/src/blocks`, so the block needs no lint exception — and a screen that draws its own dashed card still fails.
- **`ScheduleStatusBadge`** — every state of `Release` (RFC §5.2), `Automation` and `ScheduleRun` (§5.3) and of an approval, as a Kumo `Badge` with an icon and the state's word: draft outline `PencilSimpleLine`, waiting for approval `warning` `HandPalm` (+ an outline `ClockCountdown` badge with `timeLeft`), scheduled outline `CalendarBlank`, publishing/running `info` with a turning `CircleNotch` inside `role="status"`, published/ran/active `success`, conflict/failed/missed/broken `error`, expired/canceled/skipped/stopped/paused `secondary`, paused by Cloudhal and over budget `warning` (`PauseCircle`, `Gauge`), ended/due outline; approvals: approved outline `CheckCircle`, automatic `warning` `Lightning`, denied `error` `Prohibit`. A `reason` makes it a toggletip button (keyboard too, and in the accessible name). `data-subject`/`data-state` for tests.
- **`ScheduleItem`** — `variant="chip"`: a button at least 24 px tall (SC 2.5.8) with the look's icons, the time (`tabular-nums`) and the truncated title; its accessible name is the whole sentence (`scheduleItemSentence`: "09:00, Publish, Election results, proposed by Desk, Waiting for approval, 3 h left", or the screen's own `entry.label`). `variant="row"` (the agenda, the "+N more" popover, the phone day list): time, kind icon with its word for screen readers, the title (`Link` when `href`, struck through when struck), `meta` (collection, locale, terms), `origin` (`ActorBadge` + `ModeBadge subtle`), the status badge — none for the quiet "Scheduled", the approval's own badge for approved or automatic — and `actions` (Deny/Approve, the ⋯ menu whose "Move to…" is the single-pointer twin of dragging, SC 2.5.7); it wraps on phones.
- **`CalendarMonth`** (Month view, RFC §15.2, §15.7) — a WAI-ARIA APG date grid on a fixed Kumo `Table` (`role="grid"`, seven columns from `weekStartsOn`, short weekday headers with the long name for screen readers) with **one tab stop** and a roving `tabindex`: arrows by day and week, Home/End to the week's ends, PageUp/PageDown by month (Shift: year) — leaving the shown weeks asks `onMonthChange(month, day)` and focus follows; Enter or F2 into the day's chips (arrows between them; chips are never tab stops), Escape back to the day. Cells are named by the screen (`labels.day`: "Monday 12 October, today, 3 items: 2 publishes, 1 waiting for approval"); today has `aria-current="date"`; past days and weekends are `bg-kumo-recessed`; entries land on their day in the site zone (23:30 UTC is tomorrow in Istanbul). At most `maxChips` (3) chips, then a "+N more" `Popover` with the day's rows. **Moving:** with `onMove`, chips of `movable` entries (future, not running, not locked, not an occurrence — the screen decides) drag onto another day (native drag and drop on desktop chips, no drag library), and Alt+arrow on a focused chip is the keyboard twin; both only call `onMove({entry, fromDay, toDay, via})` — the screen opens `RescheduleDialog` with the old time on the new day, nothing is optimistic. A polite `role="status"` region speaks the screen's `announcement`. **Phones** (`density="dots"`, or `auto` at ≤ 640 px through `matchMedia`): a cell is the day number and up to three dots in the looks' tones plus a warning approval dot (decorative; the cell's name carries the counts), the whole cell is the target and selects the day (`aria-selected`, Enter or Space), and the chosen day's rows show under the grid ("Today · Monday 12 October", or `labels.emptyDay`).
- **`AgendaList`** (Agenda view, the default on every width) — entries grouped by their day in the site zone under **sticky** `h3` day headings (`top-12`, under the top bar, `border-b border-kumo-line`; `stick="top"` inside other scroll containers), rows in a `divide-y` list; today gets a "Now" rule (a danger hairline with the word, read by screen readers) between past and future, its finished items fold behind a ghost "3 done today" (`aria-expanded`), and a day's recurring runs past `foldRecurringAfter` (3) fold behind "21 more automation runs". Loading = `SkeletonLine`s with a status line; nothing = a frameless `SectionEmpty` (`CalendarDots`) with the screen's `emptyContents`; cursor paging = a secondary "Load more" (`loading`). The view switch tells screen readers the agenda is a complete equivalent of the month.
- **`CalendarNav`** — a `fieldset` named by `labels.group`: secondary square ‹ › buttons (`aria-label`) around "Today" (disabled while today is shown), the period ("October 2026") in a polite live region, a `goTo` slot for the screen's "Go to date" `Popover` + `DatePicker`, and the Agenda | Month segmented `Tabs` with `viewHint`. Shortcuts (`j`/`k`, `g t`, `a`/`m`, `g d`) are the screen's and call the same handlers.

### 2y. Body editor (RFC-0014 phase 1)
Markdown bodies (article bodies, page `richText` sections in markdown) are edited with **`MarkdownEditor`** from **`@cloudhal/ui/editor`** — its own subpath, like `/charts`, because Tiptap and ProseMirror are about 620 kB minified (190 kB gzip) with the menus. Studio reaches it only through `components/BodyEditor.tsx`, which `React.lazy`-loads it with the first body on screen and shows the plain Markdown `InputArea` until then; the editor's modules are in `bundle-budget.ts`'s `LAZY_ONLY`. Words come from the lazy namespace `bodyEditor` (§1), loaded with the article and page editor routes. HTML bodies keep the plain `InputArea`.
- **Markdown is the only stored format.** The editor never stores HTML or its own JSON. Loading splits the body into top-level blocks with `marked` (GFM, as the site renders); saving compares each block with what the editor would write for the original and **keeps the original bytes of every untouched block** — opening and saving changes nothing, and editing one paragraph rewrites that paragraph only (`editor/markdown-blocks.ts`, tests in `markdown-editor-codec.test.tsx`).
- **Nothing is silently rewritten.** A block the editor cannot keep exactly — raw HTML, link definitions, a ```` ```surface ```` fence (RFC-0020 §5, whose info string a code block would cut), or anything whose rendered HTML would change after a trip through the editor (`isLossy`) — is a **source block**: a read-only `InsetPanel variant="recessed"` with a secondary `Badge` "Markdown", the hint "Kept exactly as written. Edit it in Markdown mode." and the source in `font-mono`. It saves as written.
- **Layout:** a Kumo `Toolbar` (`size="sm"`, groups split by `border-kumo-hairline`): Bold, Italic, Strikethrough, Inline code, Link · Heading (h2), Subheading (h3) · Bulleted, Numbered, Checklist, Quote, Code block, Insert table, Divider, Image (when the host passes `onPickImage`) · Undo, Redo. Pressed formats are `aria-pressed` with `bg-kumo-tint`; buttons keep the selection (`onMouseDown` prevents focus loss). Then segmented `Tabs` **Rich text | Markdown**. The editing surface is `bg-kumo-control` with `ring ring-kumo-line` (`ring-kumo-focus` while focused), `rounded-lg`, at least 256 px tall (128 px for page sections), with content styles in `ui/styles.css` (`.ch-md-content`: 14px text, headings 20/18/16 px semibold, Kumo tokens only). Markdown mode is **CodeMirror 6** (`editor/SourceEditor.tsx`, MIT) on the same text: GFM highlighting in Kumo tokens (headings strong, links `text-kumo-link`, code and markers subtle), line wrapping, its own undo; it is a further lazy chunk (about 300 kB minified, 99 kB gzip) loaded on the first switch, with the `InputArea` as fallback. Only the GFM grammar is bundled, not the HTML/CSS/JS ones `markdown()` would add. The rich editor stays mounted, so its undo survives a switch.
- **Links** go through a `Popover` with an "Address" `Input`: only `https:`, `http:`, `mailto:`, `tel:`, `asset:` and site-relative addresses (the renderer's `safeHref` rule); anything else shows the field error and is not applied. Pasted and typed links follow the same rule.
- **Images** keep their stored `src`; `asset:<id>` shows through Studio's private content route (drafts included), other addresses as the SEO preview resolves them.
- **Read-only** forms (roles below Editor, a release lock) pass `readOnly`: a `fieldset` cannot turn off `contenteditable`.
- **Slash menu:** `/` at the start of a block or after a space (never in code) opens a `listbox` ("Insert block") under the caret — Text, Heading, Subheading, the lists, Checklist, Quote, Code block, Insert table, Divider, Image — filtered by what follows the `/` against the label, an English key and synonyms, with the UI locale's case rules (Turkish "ı"/"İ"). Arrows move, Enter or Tab inserts, Escape dismisses until the next `/`; focus never leaves the text. `bg-kumo-elevated`, `shadow-lg ring ring-kumo-line`, `rounded-lg`, options `rounded-md` with the chosen one `bg-kumo-tint`; Floating UI (through `@tiptap/suggestion`) keeps it attached while the page scrolls and flips it above near the bottom.
- **Selection toolbar:** a non-empty text selection gets a small `Toolbar` above it (`@tiptap/react/menus` `BubbleMenu`; same surface as the slash menu): Bold, Italic, Strikethrough, Inline code, Link. It stays while its link popover is open. Not on node selections or in code blocks.
- **Images from the library:** the host's `onPickImage` returns `{ src, alt? }`; Studio opens `AssetPickerDialog` (§2u) and writes `![](asset:<id>)` — an empty alt, so the site uses the library's alt text, and it stays current when the library's changes.
- **Paste:** text that reads as markdown (block syntax, `**…**`, `[…](…)`, inline code) arrives as blocks through the same codec as loading, so anything the editor cannot model becomes a source block. HTML from rendered pages (headings, lists, links, emphasis present) is left to the editor's schema; HTML that is only styled spans (code editors such as VS Code) yields to its text.
- **Source blocks** have a ghost "Edit as Markdown" button: Markdown mode opens with that block's text selected.
- **Outline:** a ghost `Button` "Outline" (`ListDashes`) next to the mode tabs, with a warning dot `Badge` counting heading problems, opens a `Popover` with the headings as a `nav` of ghost buttons indented by level; choosing one moves the caret there. The page already has its H1 (the article title, the hero), so an H1 in the body and a heading more than one level below the previous one get a warning `Badge` ("Use H2: the page has its H1", "Skips a level"). Nothing is changed automatically.
- **Preview:** the editor's preview follows unsaved edits (§2f).
- **Suggestions** (RFC-0014 phase 4): an agent's open proposals for a body (`edit_body` with `mode: "propose"`) sit above its editor — the article body, or each markdown rich-text section of a page — under a `Text` heading "Suggestions" with an info `Badge` "2 open" (`components/BodyProposals.tsx`). Each is an `InsetPanel`: an `ActorBadge` "{name} suggests", `RelativeTime`, the agent's note, then a `BodyDiff` of what accepting would change **now** (computed by `GET /api/sites/:siteId/proposals`, `content:read`), then a secondary "Reject" and a primary "Accept" (`POST …/:id/accept|reject`; deciding needs what updating the node needs — own limits for articles, `content:write` for pages). Accepting writes at once, so while the form has unsaved changes "Accept" is disabled with the hint "Save or discard your changes first." beside it — a hint, not a `Tooltip`, which would wrap the button in its own. A proposal whose blocks changed since it was filed shows a warning `Badge` "Out of date" (its `Tooltip` names the block) and the hint text in place of the diff; it can only be rejected. Accepting one that went stale meanwhile returns 409 and a danger toast. Accepted blocks keep the agent as their author with `via: "proposal"`. A suggestion of several operations lists them as a `Checkbox.Group` "Changes to accept", one `Checkbox.Item` per operation in words ("Change “First” to “Opening”", "Remove “Second.”"; "Rewrite “…”" for a replaced block, whose new text the diff shows; the agent's text as plain text, one line, at most 80 characters), all ticked; unticking one re-fetches the diff for the rest (`POST …/:id/preview`, a `SkeletonLine` meanwhile) and Accept becomes "Accept 1 of 2"; with none ticked the hint "Choose at least one change." replaces the diff and Accept is disabled.
- **Blocks** (RFC-0015 phase 6b, §2aa): body directives (`::button{…}`, `:::callout{…}` … `:::`) show as an `InsetPanel` (outline) per block (`editor/directives.tsx`), named for assistive tech by the type's title:
  - a header that is not editable text: the type's icon, its title in bold, a secondary one-line summary of its first text props, a warning `Badge` "Check properties" when the props do not fit, and a ghost `xs` "Properties" button (`SlidersHorizontal`) at the end;
  - "Properties" opens a `Popover` (320 px, scrolls past 70 % of the viewport) with the type's title and the generated `BlockPropsForm`; edits apply as they are typed and are disabled when the editor is read-only;
  - a container's inner text sits under the header and is edited in place, like the rest of the body; its untouched blocks keep their bytes;
  - a type the deployment does not list shows "Unknown block · {name}" with its attributes as the summary, the hint that it is kept and not shown on the site, and the ghost "Edit as Markdown" button; it saves unchanged;
  - the `/` menu lists the body types after the built-in blocks, with their icons and titles in the UI language (found by the English name too), and inserts the type's example.
- **Approvals** (§2m): a pending `edit_body` request shows "What approving changes in “{title}”" and the same `BodyDiff` under its prompt (`data-approval-changes`), computed when the list loads; a request that no longer applies shows none.
- **Ask AI** (RFC-0016 §3): when the site has AI on, the person holds `ai.invoke` and the server reaches Workers AI, the selection toolbar ends with a `Sparkle` button "Ask AI". It hands the whole top-level blocks the selection touches to `AiCommandDialog` (`MarkdownEditor`'s `onAskAi`, `selectionBlocks`).
- **Focus mode** (`docs/design/body-focus-mode.md`): a ghost `ArrowsOut` "Focus" button at the end of the header row (and Ctrl/⌘+Shift+\ from inside the editor) turns the editor into a full-screen modal layer (`dialog` named after the editor, the rest of Studio `inert`): a `max-w-3xl` column, a sticky top bar with the toolbar, the host's `focusActions` (the article editor's save state and Save), a "Spotlight" `Switch` (dims every block but the current one, remembered per browser) and "Leave focus"; Esc leaves and focus returns to the button. Never entered on page load.
- **Interactive blocks in the body** (```surface): the source block draws the block with the site's static preview (`previewSource` → `api.entries.previewFragment`, a frame with `sandbox="allow-same-origin"` and no scripts — same origin only so it can be sized to its content, the second exception after §2ac — cached per text) and keeps the code behind a ghost "Show code" toggle; "Edit as Markdown" still opens it. Invalid ones show the preview's problem note instead.
  - The `LayerDialog` has a "What to do" `Select` with the seven commands. "Change tone" adds a tone `Select`, "Translate" a language `Select` named through `Intl.DisplayNames`, "Your own instruction" an `InputArea` of at most 500 characters. A secondary "Run" button sits beside them.
  - While the answer streams: "Writing…", with the text as plain text in a `bg-kumo-recessed` box, and a "Stop" button.
  - Then a `BodyDiff` of selection → answer under "Suggested text". A code fence around the whole answer is dropped. "Try again" reruns.

### 2aa. Component sections (RFC-0015 phase 6a, ADR-0030)
Pages can hold **component sections**: a block type from the registry (`GET /api/sites/:siteId/block-types`, `content:read`) with its props (`components/BlockSection.tsx`).
- **Adding:** the page editor's add-section `DropdownMenu` lists the section kinds, then a `DropdownMenu.Separator` and a group "Blocks" with every type allowed in sections, each with its icon (the type names a Phosphor icon; `Cube` otherwise) and its title in the UI language. A new section starts from the type's example.
- **The card:** a `SectionCard` titled with the type's title and icon, like the other kinds.
- **The form:** **`BlockPropsForm`** from `@cloudhal/ui`, generated from the type's props schema — no code per type, for Cloudhal's types and a theme's alike:
  - a `string` is an `Input` (`type="url"` for links); `format: "markdown"` or `x-widget: "textarea"` an `InputArea`; an `enum` a `Select`, or a horizontal `Radio.Group` with `x-widget: "radio"` (enum values worded through `editor.blocks.values.*` when Studio knows them, else the value);
  - `number`/`integer` a number `Input`; `boolean` a `Checkbox`;
  - a flat object a `fieldset` with its fields; a list a bold `Text` label, then one `InsetPanel` per item headed "Item {n}" with ghost square buttons Move up (`ArrowUp`), Move down (`ArrowDown`) and Remove item (`Trash`), then a secondary `sm` "Add item" (`Plus`), disabled at `maxItems`;
  - labels and hints come from the schema's `title`/`description` (per locale when given), else the prop name in words;
  - an optional field emptied is removed from the props, not stored as "";
  - problems from the same interpreter the store runs (`validateProps`) show on their field as it is edited (for a link: "a safe link"); saving props that do not fit is refused with 422 `invalid_props`.
- **Unknown types** (a theme type this deployment no longer has): the card is titled "Unknown block · {name}", with an alert `Banner` saying it is kept but not shown on the site, and the props as read-only JSON in a `font-mono` `InputArea`. It saves unchanged.
- **Read-only** roles and release locks disable the form like any section.
- **On the site and in previews:** built-ins render escaped, framework-free markup (`.ch-callout`, `.ch-button`, `.ch-embed`, `.ch-faq` in the starter's CSS); a theme can map a type to its own Astro component in `theme.ts` `blocks`. A section whose props do not fit, or whose type no one renders, renders nothing on the site and a labelled placeholder in previews.

Composition rules verified against Kumo's own `SidebarDemo.tsx`:
- The header switcher is **not** a `MenuButton` (that auto-wraps in `<li>` and renders a bullet outside a `Menu`); it is a plain row trigger for `DropdownMenu` with `w-(--anchor-width)` content and a check on the current item — `@cloudhal/ui` ships it as `SidebarSwitcher`.
- `Sidebar.Loading` replaces `Sidebar.Content` until navigation data resolves; never render an empty menu.
- Counts and states go in `Sidebar.MenuBadge` (`4`, `Soon`, `Beta`); unavailable items are `disabled`, never hidden.
- Sub-navigation uses `Sidebar.MenuItem` → `Sidebar.Collapsible` → `CollapsibleTrigger render={<Sidebar.MenuButton>… <Sidebar.MenuChevron /></Sidebar.MenuButton>}` → `CollapsibleContent` → `MenuSub`/`MenuSubButton`.
- `Sidebar.Footer` holds **only** `Sidebar.Trigger`, as in Kumo's `SidebarFullDemo`, so it stays inside the 57 px rail when collapsed; the user menu is the avatar at the end of the top bar (`UserMenu`), reachable whether the sidebar is expanded, collapsed or a sheet. The footer is `z-2`: `Sidebar.Rail` (z-1, full height, inside the peek zone) used to cover the trigger, so hovering it started a peek, the rail slid away with the widening sidebar, the peek stopped and the rail came back — the sidebar flickered under the cursor. `Sidebar.Rail` toggles the sidebar from its edge.
- Below the mobile breakpoint the sidebar is a sheet; choosing a page closes it (`CloseSheetOnNavigate`, like Kumo's `NavTree` demo).

Rules from `sidebar.tsx`: `MenuButton` auto-wraps in `<li>`; `MenuItem` only around `Collapsible`; `tooltip` shows only when collapsed and not peekable; `GroupLabel` becomes a divider when collapsed; sub-menus via `Sidebar.Collapsible` + `MenuSub`/`MenuSubButton`; account↔site via `Sidebar.SlidingViews`; below `mobileBreakpoint` the sidebar is a sheet. Group names follow capabilities (Overview, Content, History, Automation, Settings), never product names.

## 4. Typography, spacing, colour
- **Text only through `Text`**: body 14 px (`size="base"`), `xs` 12 / `sm` 13 for captions, `lg` 16 only for headings; `variant="heading"` (16 px) and `size="lg"` (20 px) for page-level; page titles come from the blocks. Sentence case; product names title-cased; `bold` prop for emphasis; never `font-bold`, never `tracking-*`, never uppercase.
- **Spacing**: `gap-1.5` between a heading and its description, `gap-6` between blocks, card padding `px-5 py-4`, page container `p-6 md:p-8 lg:px-10 lg:py-9`, `max-w-[1400px]`.
- **Colour**: semantic tokens only — surfaces `bg-kumo-canvas|base|elevated|recessed|tint|overlay|contrast`, brand `bg-kumo-brand`, status `kumo-info|success|warning|danger` (+`-tint`), text `text-kumo-default|strong|subtle|inactive|placeholder|inverse|link`. No raw Tailwind colours, no `dark:` (Kumo themes via `light-dark()`; toggle with `data-mode="dark"`). The person chooses Light, Dark or System (the default, following `prefers-color-scheme` live) in the top bar's `ThemeSwitch`; the choice lives in `localStorage` (`cloudhal.studio.theme`, `lib/theme.ts`, synced across tabs) and an inline script in `index.html` applies it as `data-mode` (and `color-scheme`) on `<html>` before first paint, so a reload never flashes the other theme. The only fixed colours allowed are inside the preview frame, which shows the visitor-facing site (its own theme) on a light canvas.
- **Semantic badge colours**: decisions and outcomes use the status variants (success / warning / error); actor kinds and scope groups use tints (`info`, `secondary`, `outline`, `warning` for publish/rollback scopes) — never the saturated `purple`/`blue`/`neutral` fills, which out-shout the status column.
- **Edges**: `ring ring-kumo-line` (elevated) / `ring-kumo-hairline` (flat); never `border` + `shadow`; concentric radii (`rounded-xl p-1` → `rounded-lg`); sticky elements separate with `border-b border-kumo-line`; no `transition-colors` on hover.
- **Icons** (Phosphor): 16 px in nav, inline text, toolbars, card headers; 20 px icon-only buttons; 24 px top-level list-page title (`PageLayout icon`); 48 px `Empty`; `weight="fill"` only for status (banners, toasts) and the brand mark. Studio ships three weights only — regular, `bold`, `fill` (`apps/studio/phosphor-weights.ts` drops thin, light and duotone from every icon definition; a test refuses them in source). Icon-only buttons need `aria-label` and `shape="square"`.

## 7. Anti-patterns (CI-enforced where mechanical)
**Enforcement.** `apps/studio/scripts/design-lint.ts` holds the per-file rules (raw elements, class rules, entry points, ad-hoc surfaces, page anatomy, dialog rendering, card nesting, i18n, route templates). It runs three ways: in CI through `apps/studio/test/design-rules.test.ts` (`pnpm check`), by hand with `pnpm design:lint [files…]`, and **on every file an agent writes** through the Claude Code hook in `.claude/settings.json` (exit 2 sends the violations back to the agent at once). Biome additionally forbids `@cloudflare/kumo`, `@base-ui/react` and other icon sets in `apps/**`. When a rule blocks something Kumo cannot express, the answer is a new block in `packages/ui/src/blocks` (with the same rules), never an exception in a screen.

Raw `<table>/<h1>/<button>/<input>/<select>/<a>/<ul>/<p>` in screens; hand-rolled sidebars, headers, cards; raw Tailwind colours; `dark:`; `font-bold`, `tracking-*`, uppercase headings; hover colour transitions; `border` + `shadow`; nested `LayerCard`; conditionally rendered dialogs; status mutation through `Select`; `DANGEROUS_className` to restyle Kumo; a `Tooltip` used as a menu/popover trigger (`Trigger render={<Tooltip …/>}` swallows the trigger's props — nest it the other way, `<Tooltip render={<DropdownMenu.Trigger render={<Button/>}/>}/>`); hard-coded English (every string through `useT()`; Kumo's own labels through `KumoLocaleProvider`, `calendarLocaleProps` and the block labels, §2v Kumo locale); spinner-only pages; uniform `p-5` card padding; a raw `<iframe>` in a screen or any iframe without `sandbox=""`; fragments or conditionals directly inside `LayerDialog.Content`; a `<form>` around Kumo `Checkbox`/`Switch` (they are buttons and submit it); past-tense labels for audit events ("Deleted page" for a call that was denied) — use the tool's imperative name; a top bar that can shrink (`shrink-0` on sticky bars inside flex columns); rendering agent- or server-supplied text (approval prompts, skill descriptions) as HTML — always plain `Text`, never `dangerouslySetInnerHTML`; a chart or map `tooltipFormatter` / `dangerousHtmlFormatter` (Kumo inserts the result as HTML; lint `no-html-tooltip`, §2v); letting a self-approved action skip the person (approvals are decided only in Studio, ADR-0014); offering or sending `bypass` for an API key, a mode list that is not `KEY_MODES`, or letting a key become `auto` without the explicit consent checkbox (ADR-0015); offering an elevation to a mode that is not above the key's own, or elevating to `auto` without that same checkbox (ADR-0016); extending with any mode but the one in force, re-elevating a key whose elevation has ended from a notification, or changing an elevation outside `useExtendElevation`/`useEndElevation`; announcing a notification twice, or announcing what was there on the session's first load (§2n).

## 8. Review checklist
Before merging UI: `pnpm design:lint`; look up components with `pnpm kumo ls` / `pnpm kumo doc <Name>` / `pnpm kumo blocks` before writing markup; screenshot every touched screen at 1440 and 390 px with `pnpm design:shots -- <routes>` (headless Chrome against your dev server; fails on sideways scrolling or console errors; `SHOTS_SCHEME=dark|light` and `SHOTS_LOCALE=tr` for both themes and Turkish; for role-gated screens, one run per role's test account) and compare against this document; run `pnpm --filter @cloudhal/studio test` (design rules); confirm every new string exists in `en.ts` and every `<locale>.ts` (`test/i18n.test.tsx`); confirm the kumo-design rules (14px, sentence case, tokens) by reading the diff.
