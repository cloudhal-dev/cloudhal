# Cloudhal threat model (alpha)

Cloudhal lets AI agents change websites. The central security promise: **an agent can only do what its scopes allow, every change is recorded and reversible, and nothing goes live without a person.** This page lists who can do what, the controls behind each promise, and the risks we accept for the alpha. Report vulnerabilities as described in [SECURITY.md](../../SECURITY.md).

## Principals
Staff roles are named sets of scopes (RFC-0005, ADR-0018). A person's role is read from their single membership on every request; without one they have no scopes.

| Principal | How it authenticates | Can do |
|---|---|---|
| Owner | Better Auth session cookie (Studio) | Everything (`*`), including transferring ownership; exactly one per deployment |
| Administrator | Session cookie | Every non-wildcard scope: content, structure, publish, rollback, site settings and domains, members (non-Owner), invites up to Administrator, others' agent keys (revoke, end elevations) |
| Editor | Session cookie | Content, pages, taxonomies, redirects, publish, rollback, all Activity; invites Contributors and Authors |
| Author | Session cookie | Own articles in any status; publishes own-only change sets (anything wider becomes a request an Editor decides) |
| Contributor | Session cookie | Own never-published drafts (draft/review); proposes tags; never publishes |
| Agent | API key (`x-api-key`) with explicit scopes | MCP tools only, within its scopes narrowed to its creator's current role; publish/rollback/delete wait for a person |
| Local developer's agent | `cloudhal mcp` over stdio | All scopes on the local project; gated tools ask in the MCP client |
| Automation key | API key (`x-api-key`) minted for one automation by the person who created it (RFC-0008) | An agent key that works only inside its automation's run windows (outside them only `begin_run`, `get_mode` and `pause_automation` answer); narrowed to its owner's current role, capped by the automation's mode cap, never `bypass`; within budgets; read, label and hide only once its run reads visitor-supplied text |
| Scheduler | System actor (`sys_scheduler`) inside the admin Worker or the Node process; no credential | Publishes releases on behalf of the person who approved them, runs built-in jobs, opens and closes run windows (RFC-0008) |
| Operator | Deployment token (bearer) | Export/import whole sites (`cloudhal push/pull`); recover ownership (`cloudhal owner transfer`); export/import reader comments, with commenters' emails (`cloudhal comments export|import --remote`, RFC-0007); read the scheduler's status and run a tick (`cloudhal schedules status|list|run-due --remote`, RFC-0008) |
| Site visitor | — | Published pages; drafts only with a signed preview link; sends analytics beacons, which count only for published pages (RFC-0006); sends comments and reports, which are held for moderation (RFC-0007) |

## Promises and controls
1. **Agents stay inside their scopes, and an agent never exceeds the person whose key it uses.** Agent principals are refused on the REST API (403 everywhere except `/api/me`); MCP calls pass the policy engine (scopes × tool annotations × declared skill). A key's scopes must fit its creator's role when it is minted, and on every call they are narrowed to the creator's *current* role; a key whose creator is no longer a member is refused (401). Key modes and elevations are capped by the role (Contributor: `edits`); only the key's creator grants an elevation. Person-only scopes (`site:settings`, `members:*`, `agents:manage`, `audit:read`, `automations:manage`) never sit on a key. Keys cannot mint keys; permissions are server-only, and Better Auth's own `/api/auth/api-key/*`, `/api/auth/organization/*` and `/api/auth/admin/*` endpoints answer 404. Per-key rate limit 600/min.
2. **Nothing goes live without a person, unless the owner chose otherwise.** Publish, rollback and delete create a pending approval that a signed-in person decides in Studio (ADR-0014). The only exception is a key the owner put in `auto` mode, permanently or for a bounded time (5 min to 24 h, ADR-0016): it may publish article-only changes (nothing removed, at most 20) without a person (ADR-0015). Rollback and delete always wait. Modes are owner-only, never grant scopes, `bypass` is local only, and an elevation ends by itself because the mode is computed on every call. An agent may *ask* for an elevation (`request_elevation`), but only a signed-in owner of its key can grant it, for at most the time asked. Approvals are single-use and bound to the tool, exact arguments, the requesting agent and the content state; any change after the question voids them. Agents never receive a redeemable token. Scheduled publishes are approved by a person (or by an `auto`-mode key within its elevation window and 24 hours) against the exact pinned versions, re-checked when they run, executed at most once and never early; content scheduled for later is locked against edits and held back from ordinary publishes (RFC-0008).
3. **Every change is recorded and reversible.** Each MCP mutation snapshots the site; every tool call and decision is written to the audit log; rollback moves the published pointer to an ancestor snapshot.
4. **Agent-written content cannot run code. The only client scripts a site runs are Cloudhal's first-party scripts under `/_cloudhal/` (hashed, self-hosted, each switchable off): the analytics script and, on pages with an open comment form, the comments module and its proof-of-work worker. The CSP allows no inline or third-party scripts; the one exception is Cloudflare Turnstile on comment pages, when the owner turns it on.** Agents write markdown only (no HTML sections, no edits to HTML bodies); markdown escapes raw HTML; links and image sources are limited to safe schemes. Site HTML on Cloudflare carries `script-src 'self'; connect-src 'self'; form-action 'self'` and `Referrer-Policy: strict-origin-when-cross-origin` (`cloudhal dev` and Node serve no CSP; see the accepted risks). The analytics script (`/_cloudhal/p.<hash>.js`, ≤ 1 KB gzipped, plus the sampled vitals module `/_cloudhal/v.<hash>.js` with `web-vitals`) is bundled at build time, served as an immutable static asset from the site's own origin and loads nothing from a third party. It is injected only into published `200` HTML while the site's setting is on, never into previews, errors or feeds (RFC-0006 §5.1). The comments module (`/_cloudhal/c.<hash>.js`, ≈ 2 KB gzipped, budget 4 KB) and its worker (`/_cloudhal/cw.<hash>.js`, ≈ 0.8 KB, pure-JS SHA-256, no WebAssembly) are built the same way, referenced only by pages whose thread is open, and store nothing on the device (no cookie, no `localStorage`). With Turnstile on, such a page carries its own policy adding `https://challenges.cloudflare.com` to `script-src` and `frame-src`; every other page keeps the default (RFC-0007 §7.6). `comments.available: false` in `cloudhal.json` removes the module and its endpoints from the deployment.
5. **Studio sessions are not usable cross-site.** State-changing `/api` requests must be same-origin; cookies are HttpOnly + SameSite=Lax; `/mcp` refuses foreign origins; a server without auth only answers localhost host names.
6. **A fresh deployment cannot be claimed by a stranger, and after the owner only invite links let people in.** The first (owner) account needs the one-time setup link printed by `cloudhal deploy`; afterwards sign-up is closed. Invites are `chinv_` + 256 random bits, stored only as a SHA-256 hash, shown once, delivered in the URL fragment, single use (one guarded statement), revocable, bound to one email and one role, and expire (7 days by default, 1 h–14 d, Administrator invites ≤ 72 h). The invite and reset endpoints take JSON only and are rate-limited per IP; accepting refuses while another user is signed in. Tokens and hashes never appear in audit rows.
7. **Drafts stay private.** Previews require signed, expiring, site-bound tokens, are never cached, and their HTML is sandboxed (CSP `sandbox`).
8. **People stay inside their role; the server decides, never the UI.** REST is default-deny: every route declares its requirement in `ROUTE_SCOPES` (`packages/api/src/scopes.ts`) and a test fails for any undeclared route. Own-limited roles may only touch entries they (or their agents) wrote; `author` is set by the server. An Author's publish goes live only when every public change is their own, otherwise it becomes a request someone with the full power decides. Only someone who could make a call right now may approve it, and nobody approves their own request. Membership changes go through audited routes only; demotion narrows keys at once, removal revokes sessions, disables keys, cancels invites and denies pending requests. Studio's gating is cosmetic.
9. **Media cannot become a vector (RFC-0004).** The server sniffs every file's type from its bytes and refuses a declared type or extension that disagrees, active content (HTML, XML, scripts), archives and executables. Photos lose Exif/GPS, XMP, IPTC and comments by default (lossless; only people may keep them); AVIF with metadata is refused. SVG is validated and rejected rather than sanitised (no DTD or entities, allowlisted elements and attributes, no handlers, script URLs or external references), only people may upload it, and it is served under `CSP sandbox`. Every media response carries `nosniff`; data files are attachments. Blob keys are derived from validated ids (`media/<siteId>/<sha256>`), every adapter checks keys and the filesystem adapter checks containment. A media URL serves only what the published snapshot (or a preview token's target) contains.
10. **The server never fetches into private networks.** `fetch_asset_url` and `cloudhal media import-urls` take https on port 443 only, no IP literals or internal names, check every resolved address (IPv4, IPv6, mapped and NAT64 forms) against private, loopback, link-local and metadata ranges, follow at most 3 redirects with each hop re-checked, enforce size, time and content-type limits, and honour a per-site host allowlist. On Node the connection is pinned to the checked address.
11. **Analytics store no personal data by default (RFC-0006, ADR-0021).** No cookies or device storage, no client identifier; no IP address, user agent, city or full referrer is ever stored, and the stored contract (`AnalyticsEvent`, `additionalProperties: false`) has no field for them. Opt-in unique visitors use a random daily salt that is deleted, and GPC and DNT are honoured (the view is counted, never hashed). People and agents see aggregates only. Controls and residual risks: [Site analytics](#site-analytics-rfc-0006).
12. **No reader comment becomes public without a person (RFC-0007, ADR-0022).** Every guest comment waits for approval; agents may label and hide but never approve or reply on the site's behalf; comment text is plain text everywhere and reaches agents only as quoted, untrusted data. No IP address is stored, emails are encrypted and visible only to Editors and above, and erasure is built in. Controls and residual risks: [Reader comments](#reader-comments-rfc-0007).
13. **Embargoes and expiries hold without a scheduler (RFC-0008, ADR-0023).** The published site checks every page's and entry's time gates on each request, keeps embargoed content out of every route, list, feed, sitemap and search output until its time, and never caches a page past the next gate. Unattended agent runs work only inside their window, within budgets, and lose the ability to write once they read visitor-supplied text. Controls and residual risks: [Schedules](#schedules-rfc-0008).

## Site analytics (RFC-0006)
A cached page view never runs the site Worker, so the browser reports it: one first-party beacon per view to `POST /__cloudhal/e`, which anyone can call. The goal is not to prove that a person sent it, but to keep inflation bounded and to make pollution unable to store free text. "Mitigated" is what the code does today; "Residual" is what remains.

| Threat | Mitigated | Residual |
|---|---|---|
| **Beacon spam and count inflation** | `Sec-Fetch-Site` must be `same-origin` when present; without it, the `Origin` (else `Referer`) host must equal `Host`. The request host must be one of the site's hosts (`Site.domains`, `CLOUDHAL_SITE_HOSTS`, the Worker's own `*.workers.dev` host). Body ≤ 2,048 bytes (`Content-Length` and a capped, strict UTF-8 read). A `User-Agent` is required (≤ 512 characters); bots, crawlers, headless browsers and HTTP libraries are dropped. Precompiled schema check. Per isolate, 30 page views and 30 vitals per client per minute, keyed by `HMAC(random per-isolate key, IP)` (no IP kept; at most 20,000 clients per isolate and minute, further ones dropped). With `analytics.rateLimit`, a Workers Rate Limiting binding adds a limit across isolates (120 beacons per client and minute by default, per Cloudflare location), keyed by an HMAC of the IP under a key derived from the deployment's purge token; it fails open. The client address is the one the runtime vouches for (Cloudflare's `CF-Connecting-IP` on the Site Worker, the socket address on Node), never a header a client sent. Vitals must carry the site's current sampling. Every outcome answers `204 no-store`, so the endpoint is no oracle. | Headers are forgeable outside a browser: a determined sender can inflate counts for real published pages. Without `analytics.rateLimit`, limits are per isolate, not global; with it, per Cloudflare location and eventually consistent (and its availability on Workers Free is unconfirmed, RFC-0006 A3). The "possible bot traffic" check (RFC-0006 §5.5) makes a flood visible — Studio's banner, REST `…/analytics/bots`, `get_analytics.botTraffic` — when the busiest hour of a period's last 7 days has ≥ 200 page views and ≥ 10× the median hour, with ≥ 80 % direct entrances or one browser family; it is a heuristic: a flood spread thin, with forged referrers and mixed user agents, stays below it, and a burst from chat apps (no referrer) can trip it. Accepted, as for every analytics product. |
| **Data poisoning (fake pages, wrong attribution)** | The beacon path is percent-decoded, lower-cased and resolved against the **published** snapshot (pages, entries, archives including `/page/n`); anything else is dropped, so drafts, previews and invented paths store nothing. The node id comes from that resolution: the beacon contract refuses client node ids and client identifiers. Every built event is checked against the stored contract. | None beyond inflating real pages. |
| **Write-quota exhaustion** | Server-side `render` events (redirects, 404, 410, 451, 5xx, cache-miss HTML) are capped at 120 a minute per isolate, then sampled 1 in 10, and past 1,200 a minute 1 in 100, each weighted by `sampleOneIn`. `writeDataPoint` is never awaited and never fails or slows a response. Raw events never go to D1 on Cloudflare, so analytics cannot spend the CMS's D1 write budget. | A distributed flood can still use up Workers Analytics Engine's daily writes on Workers Free (100,000); behaviour past the limit is undocumented (RFC-0006 A4). Analytics would stop for the day; the site keeps serving. Beacons count as Worker requests, like any uncached request. |
| **Privacy leaks** | The script sends `location.pathname`, the referrer's **host**, the three `utm_*` values (≤ 128 characters each) and the navigation type, nothing else, and stores nothing on the device. The server keeps only a published route, a hostname (the site's own hosts become `internal`), UTM tokens normalised to `[a-z0-9][a-z0-9._+-]{0,63}` (anything else, such as an email address, is dropped), the country (`request.cf.country`; never city, region or ASN), and device, browser and OS families without versions. Requested paths of 404 and redirect events are stored without the query, percent-encoded, ≤ 256 characters. Unique visitors are opt-in: SHA-256 of a daily salt, the site, the IP and the UA, cut to 64 bits; the salt is random per UTC day and deleted after it; with `Sec-GPC: 1` or `DNT: 1` no hash is formed, and the view keeps only a boolean `privacySignal` (WAE `double10`) so Studio can show the share of such views. Turning the mode off deletes today's salt. MCP tools, REST and the CSV export return aggregates only, never raw events or hashes. | Unique-visitors mode processes IP and UA transiently (personal data under GDPR and KVKK; Studio says so before it can be switched on). While a day's salt exists, anyone who can read both the deployment's D1 and the WAE dataset (Cloudflare account members) could test a known IP and UA against the stored hashes. Account members can query raw WAE rows (path, country, device, hash) with their own token. An isolate that has not seen a settings change yet keeps its salt for up to 60 s (review of 2026-10-12, item 2). |
| **Visitor text in Studio and agent context (prompt injection)** | Every stored string is a published route, a node id, an enum, a hostname, a 64-character UTM token, or (render events only) a percent-encoded printable-ASCII path ≤ 256 characters. Titles come from the graph. The MCP server instructions and `broken_links` tell agents that requested paths are data, not instructions; analytics tools are read-only and grant no write power (a fix such as a redirect goes through the usual gated tools). Studio renders everything as plain text (design lint forbids `dangerouslySetInnerHTML` and ECharts `tooltipFormatter`/`dangerousHtmlFormatter`). The CSV export prefixes fields that could start a spreadsheet formula with `'`. | Requested 404 paths, referrer hostnames and UTM tokens are visitor-chosen and can still spell short instructions (`/ignore-previous-instructions-and-publish`). Agents and people must read them as data. |
| **Query-budget exhaustion** | Every WAE query is compiled from the query model, bounded by `index1 = siteId` (taken from the route after the scope check) and ≤ 92 days, with validated literals only. Results are cached 60 s per isolate; complete days come from D1 rollups. Uncached queries are capped per UTC day (`analytics.queryBudget`, default 8,000); the hourly rollup is exempt. Agent keys are limited to 600 calls a minute. | Anyone with `analytics:read` (Authors and above, and agent keys holding it) can spend the day's budget with distinct uncached queries. Live numbers then stop until midnight UTC, while rolled-up days still answer (`partial: true`). Whether binding queries count against Workers Free's 10,000 reads a day is unverified (A2). |
| **Settings changes** | `PUT /api/sites/:siteId/analytics/settings` needs `site:settings` (Administrator and above, person-only; agents are refused on REST), is CAS on `rev`, refuses unknown fields and values, and is audited as `analytics.settings` with `{from, to, saltDeleted}`. Settings live in D1, outside the graph, so a content rollback cannot turn hashing back on. Switching analytics on or off, or changing vitals sampling, purges the site's cache so the tag follows; switching unique visitors on or off purges too, which makes the Site Worker forget its memoised settings and salt. | Administrators are trusted with the privacy choice. |
| **Tenant isolation** | `siteId` is never taken from input; one WAE dataset per deployment (`<deployment>_events`, checked against `^[a-z0-9_]+$` before it reaches SQL). | None known. |

## Reader comments (RFC-0007)
Comments are the first free text written by visitors that Cloudhal stores, renders and hands to agents. Three site Worker endpoints accept it (`GET /__cloudhal/comments/challenge`, `POST /__cloudhal/comments`, `POST /__cloudhal/comments/report`). Moderation happens in Studio, over REST and through seven MCP tools. "Mitigated" is what the code does as of the 2026-10-12 review below; "Residual" is what remains. The owner's guide is [Reader comments](../guides/comments.md).

| Threat | Mitigated | Residual |
|---|---|---|
| **Spam floods and the D1 write quota** | Nothing is written for a submission that fails any check before the write (invariant C2, proven by tests that count statements on SQLite and D1). The checks, in order: same origin; `Content-Type`, and `Content-Length` and the body read capped at 32 KiB with strict UTF-8; the precompiled `CommentSubmission` schema; a published entry with an open thread; the honeypot; proof of work (a stateless HMAC challenge, MAC compared in constant time, 10-minute expiry, 3-second minimum fill time, 18 bits rising to 20 and 21 as the day fills) or Turnstile; rate limits per isolate (keyed by `HMAC(per-isolate key, network)`, an IPv6 address by its /64 like the D1 limits and the hash; requests without a client address share one separate bucket limited to 1 submission and 5 challenges a minute together), from D1 (5 stored an hour and 20 a day per client), and optionally across isolates (`COMMENTS_RL`); content rules; a per-site daily cap (1,000 stored a UTC day by default, about 7 % of D1 Free's writes); bans. A missing monthly salt is created inside the write's own batch. Proof is checked before rate limits, so unsolved requests cannot use up a real reader's allowance. Honeypot, bad proof, duplicates and bans are answered like a stored comment. | Every POST is a Worker request, so a distributed flood can still use up Workers Free's requests. A determined sender can fill the daily cap, which pauses comments (not the site) until midnight UTC. Posts from browsers without JavaScript carry no proof and no Turnstile token: under proof of work they are on by default and bounded by their own limits (1 per client per 10 minutes, 20 per site a day); with Turnstile on they are refused (`script_required`) unless the owner explicitly allows them there too (`allowWithoutScriptWithTurnstile`), in which case they bypass Turnstile within the same limits. Requests without a client address (none on Cloudflare, where `CF-Connecting-IP` is always set) rate-limit each other in their shared bucket; an IP ban never targets their shared hash, so only an email ban reaches them. |
| **Markup and script injection** | The `Comment` contract allows plain text only (`format: "text"`) and refuses bidi overrides. Normalising removes control characters, bidi embeddings, directional marks (LRM, RLM, ALM) and zero-width characters (ZWSP, ZWNJ, ZWJ outside emoji sequences, WJ, BOM) before the checks, so they cannot split a blocked word or hide in a name. Names and text are HTML-escaped (`& < > " '`). Only `https:` URLs with a dotted host and no credentials become links, with `rel="ugc nofollow noopener noreferrer"`; golden tests use hostile text (invariant C7). The article's JSON-LD carries up to 10 approved comments, serialised with `<`, `>` and `&` escaped as `<`, `>` and `&`, so it cannot close its `<script>`. Studio's design lint forbids `dangerouslySetInnerHTML` and `.innerHTML =`. | Homoglyph names and look-alike links remain possible. Imported comments may still hold directional marks and zero-width characters (the contract allows them, so other systems' data and Persian text stay valid). |
| **Prompt injection** | Reader text reaches agents only inside `<reader-name>`, `<reader-text>` and `<reader-report>` blocks, after a preamble saying it is untrusted data, with `&`, `<` and `>` escaped so a block cannot be closed from inside — in the text content and in `structuredContent` alike (the same strings, plus `untrustedNotice` and `untrusted: true`), so a client that hands either channel to the model hands it quoted text. Caps: 50 comments, 280 characters per text by default (2,000 on request), 80 per name, 500 per report detail, 20,000 characters per call for names (readers' and staff's), texts (staff replies included) and report details. Comments that address an AI get the `instruction-like` label. Tools take ids and enums and never act on comment text. Approving, restoring, replying and opening a thread wait for a person in every mode, local `bypass` included (§10.2). There is no tool to delete, erase, ban, export or change settings. | A fooled agent can mislabel, hide or hold legitimate comments (reversible, audited). |
| **Personal data exposure** | No IP address is stored, only `HMAC(salt of the month, siteId ‖ address)`, with IPv6 cut to /64. Salts are random, created per UTC month and deleted when two months old. Hashes and challenge ids are cleared after at most 30 days (`retention.clientDataDays` accepts 1–30; the job clamps stored values), matching the privacy notice. The address is the one the runtime vouches for: `CF-Connecting-IP` on the site Worker, Astro's `clientAddress` on Node. Emails are AES-GCM encrypted with the site id bound as associated data, plus a keyed HMAC for lookups, under keys derived from `CLOUDHAL_COMMENTS_KEY`. Only the `commenters` routes return them, to people with `commenters:data` (Editor and above); a lookup by email is a POST with a JSON body, so no address is ever in a URL. The contract has no field for an email, IP, hash, user agent or challenge (invariant C1). Audit rows hold ids, actions, reason codes and counts; since this review, a declined local approval no longer audits the raw arguments (item 1 below). Exports carry emails only with `personal=1` (needs `commenters:data`) or the deployment token; the CLI writes them only to an owner-only file. | Cloudflare account members with D1 access can read names, texts and ciphertexts; with the secret they can decrypt emails. IP hashes can be tested against a known address while the month's salt exists. Servers without a membership source (auth-less `cloudhal studio --no-auth`) treat every person as holding every scope, as for all routes. On Node, Astro derives `clientAddress` from `X-Forwarded-For` if a self-hoster configures `security.allowedDomains`; Cloudhal does not. |
| **Takedown latency** | Moderation never purges directly: the change and its `cloudhal-comments-<nodeId>` purge row are written in one batch (invariant C6). Takedowns (an approved comment hidden, marked spam, held, deleted or erased; a thread hidden) are flushed first, 2 s after the write, through the site Worker's purge endpoint. Normal purges wait 20 s and only while the last minute shows fewer than 3 purge requests, so publishing always finds room. Failures back off (30 s × 2^attempts, at most 5 min). After 2 minutes a waiting takedown raises a notification, with a last-resort "purge the whole site cache". The hourly job is the backstop; it runs behind an hourly watermark on the scheduler's minute tick (cron, or the `SchedulerClock` Durable Object alarm where the account has no free cron slot; RFC-0008). | Browsers and other caches may keep a copy. An empty purge bucket delays removal by up to a minute or two. Whether a 20 s `waitUntil` survives on Workers Free (V5) and the purge budget under real load (V1) are still to be verified live. |
| **Abuse of reports** | A report never changes a comment's status. Reports need the same proof as comments, are limited to 5 per client an hour and 200 per site a day, and only approved comments can be reported. Details are cut to 1,000 characters and shown as plain text. | A flood of reports can bury real ones; the limits bound it. |
| **Approval replay and stale decisions** | Approvals for comment tools are bound to a `cm1:` hash of the named comments (id, rev, status) and threads (rev, effective state) instead of the graph (invariant C4). Carrying out recomputes the hash as the approving person and answers 409 `state_changed` on a mismatch. The binding fails closed: if it cannot be computed when the agent asks, nothing is filed (or minted for a local question) and the call answers `state_unavailable`; a request without a computed binding, or one whose binding cannot be computed when the person decides, is denied with 409 `state_changed` and never carried out. Approvals are single use (`pending → approved → consumed`), and agents cannot redeem them. | A store outage at decision time closes the request; the agent must ask again. |
| **Cross-site posting** | `Sec-Fetch-Site` must be `same-origin` when present; otherwise the `Origin` (else `Referer`) host must equal `Host`, and `Host` must be one of the site's hosts (`Site.domains`, `CLOUDHAL_SITE_HOSTS`, the Worker's own `*.workers.dev` host). There are no cookies and no ambient authority to forge. The page to return to is computed by the server (no open redirect). | Headers are forgeable outside a browser (bounded by proof and limits). On Node every request host is accepted as a site host. |
| **Third-party script (Turnstile)** | Opt-in per site; the CSP is widened only on pages with an open form. `siteverify` gets the owner's secret (stored encrypted, write-only), `remoteip` and an idempotency key. The answer's hostname must be a site host and its action the form's kind. Any failure, an outage included, answers 503 (fails closed). | Cloudflare processes visitors' browser data while it is on; the privacy notice has a variant for it. Posts without JavaScript are off while it is on, unless the owner explicitly allows them (they then bypass it; see the first row). Whether a `workers.dev` hostname is accepted is unverified (V2). |
| **D1 limits per invocation** | Every export is paged, Studio's REST export (`GET …/comments/export`, also with `personal=1`) like the deploy-token one: 500 comments (10 reads) or 100 commenters (4 reads) per request, continued with `cloudhal-next-cursor`. A commenter's export reads their comments in one query. "Ban and hide past comments" hides at most 1,000 comments a request in set-based batches of 200 and answers `more` (Studio repeats it). Bulk moderation and erasure use set-based statements (≤ 5 per batch, whatever the number of comments). Tests count every query of a request on SQLite and D1 against 3,100 comments and 121 commenters. | Queries spent by authentication (session and membership reads) come on top; the measured requests leave more than half of the 50 free. |
| **Tenant isolation and keys** | The site Worker uses its own `CLOUDHAL_SITE_ID`, and REST uses the route's site after the scope check (invariant C14); every query is keyed by it. `CLOUDHAL_COMMENTS_KEY` is generated by `cloudhal deploy` (256 bits), kept in the 0600 secrets file and given to both Workers as a secret, never in a config. Without it (or shorter than 32 characters) comments are unavailable, never a crash. Proof-of-work, email, email-hash, secret and `COMMENTS_RL` rate-limit keys are derived from it by HKDF with distinct labels; the raw secret keys nothing. Imports take the site from the route, never from the file. | MCP tools take `siteId` from their arguments, like every MCP tool (roles are deployment-wide). Losing the secret makes stored emails and the Turnstile secret unreadable. |

## Schedules (RFC-0008)
Schedules add the first actions Cloudhal takes when nobody is at the keyboard: releases published by the scheduler, time gates the site enforces on its own, and agent runs started by external platforms with their own keys. "Mitigated" is what the code does as of 2026-10-13 (rollout steps 1–8, 10 and 12; built-in job bodies and Studio screens are still being built); "Residual" is what remains. The owner's guide is [Schedules](../guides/schedules.md).

| Threat | Mitigated | Residual |
|---|---|---|
| **Embargo leak through a forgotten render path** | One helper (`isAvailable`, `@cloudhal/core-ts/availability`) applied by the snapshot source at one instant per request to every public path: pages, entries, lists, archives and their counts, related posts, menus, RSS, sitemap, JSON-LD and Open Graph, the comments endpoints and analytics lookups (invariant S9). ## Accepted risks (alpha)
- **Skill narrowing is advisory.** A client that omits `_meta["cloudhal.skill"]` is limited only by its key's scopes. Bind skills to keys before treating them as a control.
- **Roles are deployment-wide.** A role applies to every site of the deployment; keys are not scoped to a site. Per-site roles come later (RFC-0005 open question 10).
- **Link invites leave the email unverified.** Whoever holds a link becomes the invitee; the account's email is marked unverified unless a mail sender delivered the link. A link pasted into a shared channel grants its role to whoever uses it first; links are single use, short-lived and revocable.
- **Administrators can demote or remove each other** (Ghost parity). Every change is audited and the affected person is notified.
- **Administrator-issued password reset links** (`chrst_…`, one hour, single use) let an Administrator take over a non-Owner account; they are audited, and never issued for the Owner.
- **The deployment token is root** for site data (read drafts, replace content). Keep `.cloudhal/deploy/secrets.json` private; rotation tooling is pending.
- **Preview tokens and agent keys do not expire by default** (preview links up to 7 days; keys until revoked). Revoke keys in Studio; shorter defaults are planned.
- **Approval prompts include agent-chosen titles** (shortened and quoted). Read the change list, not just the counts.
- **`auto` mode publishes without a person** within the low-risk rule. A wrong but small article change can go live; it is audited as auto-approved and one rollback away. Prefer a time-boxed elevation over a permanent `auto` key.
- **Local `cloudhal mcp` trusts the developer's MCP client** to ask the person (elicitation).
- **Workers cannot pin DNS.** On the admin Worker, `fetch_asset_url` checks names through DNS-over-HTTPS but `fetch` resolves again; a rebinding answer could differ. Cloudflare's egress has no route to the operator's private networks or cloud metadata, and every other rule still applies. Set a per-site host allowlist (`cloudhal.media.allowHosts`) for agents that fetch.
- **No malware scanning.** Uploads are type-checked, not scanned; data files are served as attachments. Attach a scanner to R2 event notifications if you need one.
- **A taken-down file may survive in browsers** that cached it under `immutable`; the edge copy is purged.
- **Analytics beacons can inflate counts for published pages** ([Site analytics](#site-analytics-rfc-0006)). They cannot create pages, target drafts or store free text.
- **Unique-visitors mode processes IP addresses and user agents** transiently into a daily hash. It is off by default and Administrator-only; owners should say so in their privacy policy ([guide](../guides/analytics-privacy.md)).
- **Requested 404 paths, referrer hosts and UTM tokens are visitor-controlled text** shown to people and agents, within small alphabets and lengths.
- **The AI-crawler report and the request estimates are lower bounds or estimates.** Render events see cache misses only.
- **Proof of work raises the cost of spam but does not stop a determined sender** ([Reader comments](#reader-comments-rfc-0007)). Every guest comment waits for a person anyway, and the daily cap bounds what reaches D1.
- **IP bans end when the month's salt rotates** (at most about a month); email bans last until lifted.
- **Posting without JavaScript is a weaker path**: no proof and no Turnstile, bounded by its own limits and switchable off per site. With Turnstile on it is off unless the owner allows it explicitly.
- **A published page is a function of the snapshot and of live comments.** Rollback never touches comments, so a rolled-back article keeps its discussion.
- **`cloudhal dev` and Node serve site pages without a CSP.** Only the Cloudflare site Worker sets it; a Node self-host should add one at its proxy.
- **The cron trigger has no delivery guarantee** (RFC-0008). The request backstop, the heartbeat and the one-hour window make a missed tick visible and bounded; measured on Workers Paid (2026-10-12): 0 of 106 minutes missed, p99 delay 24.6 s. Not yet measured on Workers Free.
- **Workers Cache honouring short edge lifetimes is verified live, not by contract.** Embargoes and expiries rely on it instead of purges (a 30 s lifetime held on 2026-10-12). If it ever stops, gates still hold for uncached requests and the cache keeps a page at most until its lifetime ends.
- **Agents see embargoed drafts** as they see any draft (`content:read`). Embargoes keep content off the public site, not away from keys that may read content.
- **Live analytics depend on the Analytics SQL binding** being available on the account's plan (RFC-0006 A1, unverified on Workers Free). Without it, visits are still recorded and kept for 3 months, and Studio shows "can't read yet".

## Reviews
- 2026-10-08 — pre-launch review (Sprint 7): 1 critical, 3 high, 5 medium findings fixed (agents on REST, self-approval, approval replay, agent HTML/XSS, CSRF, owner claim, scoped CAS, audit rows, no-auth host check); low items tracked above.
- 2026-10-12 — site analytics (RFC-0006 step 11): the controls above checked against the code. Items found, and their status:
  1. **Mitigated.** Without the hourly cron trigger (`CLOUDHAL_ANALYTICS_CRON=off`, Workers Free accounts with no free trigger), past salts were deleted only when someone read analytics, so a salt could outlive its day. Now the first salt of a day deletes every earlier one in the same atomic `batch()` (`getOrCreateSalt`), so no salt outlives its day by more than the first hashed page view of the next; the cron and on-read rollups still delete them too.
  2. **Mitigated.** The site Worker kept the day's salt in isolate memory after "unique visitors" was switched off and its D1 row deleted, and reused it when the mode was switched on again the same day, linking hashes across the switch. Now the memoised salt is read again from D1 whenever the isolate re-reads its settings (every 60 s, or at once after a purge), and switching unique visitors on or off purges, which resets the memo; a deleted row means a new random salt. An isolate that the purge did not reach can use the old salt for at most the 60 s it already takes to see any settings change.
  3. **Mitigated.** Off Cloudflare (`cloudhal dev` with `analytics.dev`, a future Node host) the beacon handler trusted a client-sent `CF-Connecting-IP`, which defeated the per-client limit and fed the hash. Now the handler never reads the client address from a header: the caller passes it (`clientIp`) — the Site Worker passes `CF-Connecting-IP`, which Cloudflare's edge sets and overwrites; the Node middleware passes the socket address. The Rate Limiting binding is keyed from the same address.
  4. **Mitigated.** The optional Rate Limiting binding (`analytics.rateLimit`) is built, and so is the "possible bot traffic" banner (a heuristic over aggregates; see the Site analytics table).
- 2026-10-12 — reader comments (RFC-0007 step 10): the claims of RFC-0007's Security section and invariants C1–C14 checked against the code of steps 2–7 and 10. Most hold (see [Reader comments](#reader-comments-rfc-0007)). Items found, and their status:
  1. **Mitigated.** When a person declined a gated call in their own MCP client, the refusal's audit row stored the raw arguments, so a declined `draft_comment_reply` kept the reply text and a declined `moderate_comments` its note (against C8). The row now goes through the tool's `auditArgs` like every other row (test in `mcp-server/test/comments.test.ts`).
  2. **Mitigated.** Retention (pending, spam, deleted, IP hashes and challenge ids after 30 days) ran only on the admin Worker's cron. A deployment whose account had no free cron trigger never ran it, and neither did `cloudhal studio` on Node. Now `cloudhal deploy` keeps the trigger for comments even with analytics off; without a free slot it sets `CLOUDHAL_COMMENTS_CRON=off`, and the admin Worker then runs the hourly job after requests, at most hourly per isolate. `cloudhal studio` and `cloudhal mcp` run it on an hourly timer.
  3. **Mitigated.** If the `cm1:` binding could not be computed both when the agent asked and when the person decided, both sides read `"unbound"` and the comparison passed. Now a failed binding is never a value: the MCP server refuses to file a request or mint a confirmation for it (`state_unavailable`), and Studio's carry-out denies (409 `state_changed`) a request whose stored binding is missing or whose binding cannot be computed now (`isBoundState`; tests in `mcp-server/test/comments.test.ts` and the API suite on SQLite and D1).
  4. **Mitigated.** RFC-0007 §9.1 and §9.3 promise that IP hashes and challenge ids are kept 30 days, and the site's privacy notice (§9.6) says "up to 30 days", but `retention.clientDataDays` accepted 1–3,650. Now settings accept 1–30 (`MAX_CLIENT_DATA_DAYS`, 400 above it), and the retention job and the settings reader clamp a stored value to 30, so the notice stays true whatever an Administrator chooses.
  5. **Mitigated.** Posts without JavaScript skipped Turnstile as well as proof of work, and they were allowed by default (RFC D11), so an owner who turned on Turnstile could not expect every post to be verified. Now, while Turnstile is on, they are refused (`403 script_required`, nothing written) unless the owner also sets `allowWithoutScriptWithTurnstile` (default false; `withoutScriptAllowed` decides for the pipeline, the rendered form and `cloudhal comments status`). D11 is unchanged under proof of work. The guide explains the trade-off.
  6. **Mitigated.** The MCP tools also returned comments as `structuredContent` (marked `untrusted: true`, capped) with the reader text neither delimited nor escaped, so C8 held for the text content only. Now every reader name, text and report detail in structured content is the same escaped `<reader-…>` block as in the text content, results carry an `untrustedNotice` preamble, and one 20,000-character budget covers both channels (they carry the same strings). Tests feed fake tool calls, closing tags, chat-template tokens and pre-escaped tags through both channels (`mcp-server/test/comments.test.ts`).
  7. **Mitigated (availability).** Studio's REST export, its personal-data variant, "ban and hide past comments" and a commenter's export looped past D1 Free's 50 queries per invocation on large sites. Now Studio's export uses the deploy-token export's pages (`exportPage`, `cloudhal-next-cursor`), a page of commenters costs four reads whatever its size (`SqlCommentStore.commenters`), a commenter's export is one read (`commenterComments`), and hiding past comments is set-based and bounded (`hideApprovedOf`, ≤ 1,000 a request with `more`). The API suite counts every query per request on SQLite and D1 and asserts it stays under 50.
  8. **Mitigated.** `GET …/commenters?email=` (as RFC §12 specified) put an email address in a URL query string, where request logs can keep it. The lookup is now `POST …/commenters/lookup` with `{email}` or `{commentId}` in a JSON body (`commenters:data`, people only, in `ROUTE_SCOPES`); the GET variant is gone, so a query-string lookup has no declared route (default-deny). Studio's `findCommenter` sends the POST.
  9. **Mitigated (minor).** The isolate rate limiter keyed the full IPv6 address (the D1 limits and the hash use the /64); requests without a client address shared the ordinary `"unknown"` bucket and hash; the `COMMENTS_RL` key was an HMAC under the raw secret; staff names were not charged to the 20,000-character budget (reply texts were); directional marks and zero-width characters were kept. Now the limiter keys `clientNetwork` (IPv6 /64); requests without an address share `UNKNOWN_CLIENT_KEY` with stricter limits (1 submission and 5 challenges a minute together), and `ban` skips an IP ban of their shared hash; the binding's key is `rateLimitKey` under an HKDF-derived key (`cloudhal/comments/rl/v1`); staff names are charged; and normalising removes LRM, RLM, ALM, ZWSP, ZWNJ, WJ, BOM and ZWJ (kept only between two emoji in text). The contract still allows those characters, so imported data stays valid.
  10. **Mitigated (RFC wording).** §11.2 point 6 said CSV and JSON exports prefix formula-like cells with `'`. The comments export is JSON lines meant to be imported again, where a prefix would corrupt the data, and there is no CSV export of comments. The RFC now says "CSV exports"; the one CSV export (analytics) prefixes such cells, and a test pins that the JSON-lines export keeps formula-like text verbatim.
  11. **Mitigated (gap).** "Allow comments" (RFC §10.1) had no route: `ADDABLE_KEY_SCOPES` lacked `comments:read`, so owners widened access by creating new keys. Now `comments:read` can be added to an existing key under `analytics:read`'s rules (own keys or `agents:manage`, never beyond the creator's role, so never to a Contributor's key; audited `agent-key.scopes`). Write scopes are still fixed at creation.
