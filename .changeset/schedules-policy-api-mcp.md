RFC-0008 rollout steps 7–8 — schedules for people and agents. **Policy:** scopes `schedules:read`, `schedules:write(:own)` and `releases:publish(:own)` (key-grantable; `site:publish` implies `releases:publish`) and the person-only `automations:manage`; roles per §10.2 (everyone reads the schedule, Contributors and Authors schedule their own work, Authors approve their own releases, Editors and above everything and automations); new keys get `schedules:read`, and `schedules:write` from `manual` up; abilities `schedules.*`, `releases.*`, `automations.manage`. A new `publish` call class: `plan` refuses, `manual` and `edits` wait, `auto` schedules a low-risk release only when it runs within the key's elevation or 24 hours (`checkAutoRelease`, `autoReleaseWindowEnds`), local `bypass` runs. Approvals carry `releaseId`, `runId` and an expiry (a release request stays open until the release's time; agents ask at most 30 days ahead); audit rows carry `runId`, `releaseId` and `automationId`. **MCP:** seventeen tools (`list_schedule`, `get_schedule`, `list_releases`, `get_release`, `propose_release`, `schedule_release`, `reschedule`, `cancel_schedule`, `set_embargo`, `lift_embargo`, `schedule_unpublish`, `list_automations`, `list_runs`, `get_run`, `begin_run`, `end_run`, `pause_automation`); release requests are bound to the release's `rl1:` hash and time and carried out when a person approves them; an agent's move voids the approval; lifting an embargo is always a person's (Editors and above, with a reason). Automation keys work only inside an open run, in the automation's mode cap, with the taint rule, budgets, the daily write cap and the anomaly pause enforced on every call; `get_mode` reports the run. **REST:** the calendar, releases (built on core-ts's `ReleaseService`, "Publish now" included), gates and the embargo lift, automations, runs, the kill switch, `/api/scheduler` and all in `ROUTE_SCOPES`; every API GET without its own caching header answers `cache-control: no-store`; schedule notifications; `features.schedules`. The scheduler's run-time re-check (§10.6) is wired into the admin Worker's tick and the Node ticker (`releaseApprovalCheck`: the approver may still approve it, an `auto` release's key still holds; also `createReleaseApprovalCheck`, `releaseRights`). The admin Worker, `cloudhal studio` and `cloudhal mcp` serve the schedule routes and tools. **Schedules:** the store calls behind the API and MCP (automation keys, open runs, run bookkeeping, automation edits and deletes, release titles, lateness).
